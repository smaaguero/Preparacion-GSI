## 1. Bases de datos y SGBD

### 1.1 Base de datos, esquema e instancia

Una **base de datos** es un conjunto de datos **persistentes**, **estructurados** e **interrelacionados** según un modelo de datos, y compartidos por varios usuarios y aplicaciones.

Frente a los ficheros tradicionales, donde cada aplicación tenía los suyos, la base de datos evita:

- **Redundancia e inconsistencia:** el mismo dato repetido en varios ficheros, con valores distintos.
- **Dependencia de los programas:** cambiar el formato de un fichero obligaba a cambiar todos los programas que lo usaban.
- **Dificultad de acceso y de compartición:** cada consulta nueva requería un programa nuevo.
- **Problemas de integridad, seguridad y concurrencia** difíciles de resolver en cada aplicación.

Dos conceptos que se confunden:

- **Esquema:** la descripción de la estructura de la base de datos (tablas, columnas, tipos, restricciones). Cambia poco.
- **Instancia u ocurrencia:** los datos que contiene en un momento dado. Cambia continuamente.

### 1.2 Qué es un SGBD y qué debe garantizar

Un **sistema de gestión de bases de datos** (**SGBD**, en inglés DBMS) es el conjunto de programas que permite **definir, almacenar, consultar y modificar** una base de datos, manteniendo su integridad, seguridad y disponibilidad. Entre la base de datos y los usuarios, todo pasa por el SGBD.

Lo que debe garantizar:

- **Independencia de los datos:** física y lógica (apartado 2.3).
- **Redundancia controlada:** si hay datos repetidos, el SGBD los mantiene coherentes.
- **Integridad:** los datos cumplen las reglas definidas (tipos, claves, restricciones).
- **Concurrencia:** muchos usuarios a la vez sin interferencias (apartado 5).
- **Recuperación:** tras un fallo, la base de datos vuelve a un estado correcto.
- **Seguridad y confidencialidad:** cada usuario solo accede a lo que se le permite.
- **Lenguajes de alto nivel** para definir y manipular los datos, y herramientas de administración.
- **Rendimiento** con grandes volúmenes de datos.

### 1.3 Diccionario de datos

El **diccionario de datos** o **catálogo** guarda los **metadatos**: la descripción de todos los objetos de la base de datos. Incluye tablas, columnas, tipos, restricciones, índices, vistas, usuarios, privilegios, espacio ocupado y quién creó o modificó cada objeto.

- **Diccionario activo:** el SGBD y las herramientas lo consultan y lo mantienen automáticamente. Lo que no está definido en él no se puede usar.
- **Diccionario pasivo:** es solo documentación. Los programas pueden usar definiciones que no figuran en él.

En los SGBD relacionales el catálogo es **activo** y se consulta **con el mismo SQL** que los datos (regla 4 de Codd). La norma SQL lo estandariza como **INFORMATION_SCHEMA**.

### 1.4 Lenguajes del SGBD

- **DDL** (*Data Definition Language*): define la estructura. CREATE, ALTER, DROP, TRUNCATE.
- **DML** (*Data Manipulation Language*): consulta y modifica los datos. SELECT, INSERT, UPDATE, DELETE, MERGE. Algunos autores separan SELECT como **DQL** (*Data Query Language*).
- **DCL** (*Data Control Language*): controla el acceso. GRANT, REVOKE.
- **TCL** (*Transaction Control Language*): controla las transacciones. COMMIT, ROLLBACK, SAVEPOINT.

En SQL los cuatro forman parte del mismo lenguaje (apartado 4.1). Por su forma de trabajar, un lenguaje de datos puede ser:

- **Procedimental o navegacional:** dice **cómo** obtener los datos, registro a registro. Es el caso de los modelos jerárquico y en red.
- **No procedimental o declarativo:** dice **qué** datos se quieren y el SGBD decide cómo obtenerlos. Es el caso de SQL.

### 1.5 Usuarios y administrador

- **Administrador de la base de datos (DBA):** define el esquema interno y los permisos, vigila el rendimiento, hace las copias y recupera los fallos (B4-T02).
- **Administrador de datos o diseñador:** define el esquema conceptual a partir de las necesidades de la organización.
- **Programadores de aplicaciones:** acceden a la base de datos desde un lenguaje de programación.
- **Usuarios finales:** usan las aplicaciones o lanzan consultas directamente.

### 1.6 Modelos de datos y tipos de SGBD

Los SGBD se clasifican por el **modelo de datos** que usan:

- **Jerárquico:** los datos forman un árbol de relaciones 1:N. Ejemplo histórico: IBM IMS.
- **En red o CODASYL:** los datos forman un grafo y admiten relaciones N:M. El acceso es navegacional.
- **Relacional:** los datos se organizan en tablas y se manejan como conjuntos. Es el dominante desde los años ochenta. Ejemplos: Oracle Database, Microsoft SQL Server, IBM Db2, PostgreSQL, MySQL, MariaDB y SQLite.
- **Orientado a objetos:** almacena objetos directamente. Ha tenido poco uso.
- **Objeto-relacional:** relacional con tipos definidos por el usuario, herencia y métodos. Lo estandarizó SQL:1999, y hoy lo son casi todos los SGBD relacionales.
- **NoSQL:** renuncia al modelo relacional para escalar horizontalmente. Hay cuatro grandes familias:
  - **Clave-valor:** Redis.
  - **Documentales:** MongoDB.
  - **Columna ancha:** Apache Cassandra, HBase.
  - **Grafos:** Neo4j.

  Se estudian en B3-T15.
- **NewSQL:** relacionales distribuidos con ACID y escalado horizontal, como Google Spanner o CockroachDB.

Hoy muchos SGBD son **multimodelo**: un relacional como PostgreSQL u Oracle guarda también JSON, XML, datos geográficos o texto indexado.

**INAP 2025.** Preguntó qué SGBD **no** es relacional. La respuesta era **Cassandra**, una base de datos NoSQL distribuida de columna ancha. MySQL, Oracle y MariaDB son relacionales. MariaDB nació en 2009 como bifurcación de MySQL.

## 2. La arquitectura ANSI/SPARC

### ANSI/SPARC e independencia de datos

![Arquitectura en tres niveles con vistas externas, esquema conceptual global y nivel interno físico, mostrando independencia lógica entre externo y conceptual e independencia física entre conceptual e interno.](../../assets/diagrams/b2/b2-t05-ansi-sparc.svg)

_Relaciona los tres esquemas con los dos tipos de independencia que suelen intercambiarse en test._

**Qué debes recordar:** La independencia física protege el modelo conceptual frente a cambios de almacenamiento; la lógica protege vistas y aplicaciones frente a cambios conceptuales.

### 2.1 Origen

En 1975 el comité **ANSI/X3/SPARC** (*Standards Planning And Requirements Committee* del organismo de normalización estadounidense ANSI) publicó un informe provisional sobre la arquitectura de los SGBD. El informe final, de 1977–1978, propone describir la base de datos en **tres niveles de abstracción**, cada uno con su **esquema**. Por eso se la llama también **arquitectura de tres esquemas**.

El objetivo es la **independencia de los datos**: que los cambios en un nivel no obliguen a cambiar los demás ni las aplicaciones.

La arquitectura es **independiente del modelo de datos**: vale para un SGBD jerárquico, en red o relacional.

### 2.2 Los tres niveles

- **Nivel externo o de visión.** Cómo ve los datos cada usuario o aplicación. Hay **varios esquemas externos** o **vistas**, cada uno con la parte de la base de datos que interesa a un usuario y en la forma que le conviene. Por ejemplo, la unidad de nóminas ve los datos económicos del personal, pero no sus datos médicos.
- **Nivel conceptual.** La descripción **lógica y global** de toda la base de datos para la organización: entidades, atributos, relaciones, tipos de datos, restricciones de integridad y seguridad. Hay **un único esquema conceptual**, y no dice nada del almacenamiento. En un SGBD relacional es el conjunto de tablas con sus columnas y restricciones.
- **Nivel interno o físico.** Cómo se almacenan realmente los datos: ficheros, páginas, registros, índices, compresión, particiones y caminos de acceso. Hay **un único esquema interno**. Por debajo queda el nivel físico del sistema operativo y del disco.

**Cuidado con la terminología.** El nivel externo **no se llama «lógico»**. Cuando se habla de «nivel lógico» se suele aludir al **conceptual** (el esquema lógico global). El distractor de la pregunta INAP 2022 era precisamente «Externo, Conceptual y Lógico».

**INAP 2022.** Preguntó cuáles son los niveles de la arquitectura ANSI/SPARC: **externo, conceptual e interno**. Los distractores eran «Lógico, Conceptual y Físico», «Vista, Modelo y Controlador» (el patrón de aplicaciones MVC) y «Externo, Conceptual y Lógico».

### 2.3 Correspondencias e independencia de datos

Entre cada par de niveles hay una **correspondencia** (*mapping*): la regla que traduce los datos de un esquema al otro.

- **Correspondencia externo/conceptual:** cómo se obtiene cada vista a partir del esquema conceptual.
- **Correspondencia conceptual/interna:** cómo se almacena cada elemento del esquema conceptual.

Gracias a ellas hay dos tipos de **independencia de datos**:

- **Independencia física:** se puede cambiar el **esquema interno** sin cambiar el conceptual ni las aplicaciones. Por ejemplo, crear un índice, mover una tabla a otro disco o particionarla. Solo cambia la correspondencia conceptual/interna. Es fácil de conseguir y los SGBD relacionales la ofrecen plenamente.
- **Independencia lógica:** se puede cambiar el **esquema conceptual** sin cambiar los esquemas externos ni las aplicaciones. Por ejemplo, añadir una columna o dividir una tabla en dos, redefiniendo la vista para que siga devolviendo lo mismo. Solo cambia la correspondencia externo/conceptual. Es **más difícil** de conseguir: no todos los cambios conceptuales se pueden ocultar.

**INAP 2022.** Preguntó cómo se llama la capacidad de modificar el esquema de un nivel sin tener que modificar el del nivel inmediato superior. La respuesta era **independencia de datos**. La pregunta decía «arquitectura ANSI/SQL», pero se refería a ANSI/SPARC.

### 2.4 Correspondencia con un SGBD relacional

| Nivel ANSI/SPARC | En un SGBD relacional | Se define con |
| --- | --- | --- |
| Externo | Vistas y privilegios por usuario | CREATE VIEW, GRANT |
| Conceptual | Tablas, columnas, tipos, claves y restricciones | CREATE TABLE, ALTER TABLE |
| Interno | Ficheros de datos, espacios de tablas, índices, particiones | CREATE INDEX y opciones de almacenamiento del producto |

### 2.5 El modelo de referencia DAFTG

En los años ochenta, el grupo **DAFTG** (*Database Architecture Framework Task Group*) de ANSI/SPARC amplió la arquitectura con un **modelo de referencia** para normalizar los SGBD. Separa dos ámbitos:

- **Definición de los datos:** lo que hace el administrador al crear el diccionario y los esquemas.
- **Manipulación de los datos:** lo que hacen las aplicaciones y los usuarios al usar los datos.

Sus componentes principales son:

- El **sistema de control de correspondencias** (DMCS, *Data Mapping Control System*): el núcleo del SGBD, que traduce entre niveles.
- Las **herramientas de gestión de datos** (DMT, *Data Management Tools*): lenguajes, utilidades de carga y de ajuste.
- Las **interfaces** entre ellos: el lenguaje de datos (DL) y el interno (i-DL) hacia el sistema operativo.

Una ampliación posterior añadió el **modelo de referencia de las facilidades de usuario** (UFRM). Para el examen basta saber que existe y que distingue definición y manipulación.

## 3. El modelo relacional

### 3.1 Origen y conceptos

**Edgar F. Codd** (IBM) propuso el modelo relacional en 1970, en el artículo *A Relational Model of Data for Large Shared Data Banks*. Lo basa en la teoría matemática de conjuntos y en la lógica de predicados. Los datos se representan como **relaciones**, que se visualizan como tablas, y se manipulan **como conjuntos**, sin indicar caminos de acceso.

| Término formal | Término SQL | Término de ficheros | Significado |
| --- | --- | --- | --- |
| Relación | Tabla | Fichero | Conjunto de tuplas con la misma estructura |
| Tupla | Fila | Registro | Un elemento de la relación |
| Atributo | Columna | Campo | **Una** propiedad con nombre |
| Dominio | Tipo de datos | — | Conjunto de valores posibles de un atributo |
| Grado | — | — | Número de atributos |
| Cardinalidad | — | — | Número de tuplas |

El **esquema de una relación** es su nombre con sus atributos, por ejemplo Expediente(id, fecha_entrada, estado, importe). Su **extensión** o instancia son las tuplas que contiene en un momento dado.

### 3.2 Propiedades de una relación

Por ser un **conjunto** matemático:

- **No hay tuplas duplicadas.**
- **Las tuplas no tienen orden.**
- **Los atributos no tienen orden:** se identifican por su nombre.
- **Los valores son atómicos:** cada celda tiene un solo valor del dominio, no listas ni grupos repetitivos. Es la primera forma normal.

Una tabla SQL se aparta en algo del modelo: **admite filas duplicadas** si no tiene clave, y las columnas tienen un orden de definición.

### 3.3 Claves

- **Superclave:** cualquier conjunto de atributos que identifica de forma única cada tupla, aunque sobre alguno.
- **Clave candidata:** superclave **mínima**, es decir, si se quita cualquier atributo deja de identificar. Una relación puede tener varias. **(INAP 2024: el conjunto de atributos que identifica unívoca y mínimamente cada tupla es la clave candidata.)**
- **Clave primaria** (*primary key*): la clave candidata elegida como identificador principal. Solo hay **una** por tabla y sus atributos **no admiten nulos**.
- **Clave alternativa:** cada clave candidata no elegida como primaria. En SQL se declara con UNIQUE.
- **Clave foránea o ajena** (*foreign key*): uno o varios atributos cuyos valores deben coincidir con los de una clave (normalmente la primaria) de otra relación, o de la misma. Materializa las relaciones entre tablas. En una relación 1:N va en el lado N.
- **Clave simple o compuesta:** según tenga uno o varios atributos.
- **Clave natural o subrogada:** la natural tiene significado de negocio (el NIF); la subrogada es un identificador artificial (un número secuencial).

**Clave primaria frente a UNIQUE (INAP 2025, clasificada en B3-T04).** Las dos garantizan valores únicos, pueden ser compuestas y suelen crear un índice. La diferencia ineludible es que la **clave primaria prohíbe los nulos** y solo hay una por tabla, mientras que una columna UNIQUE **puede admitir nulos**, según el gestor: Oracle y PostgreSQL admiten varios y SQL Server solo uno. SQL:2023 permite elegirlo con NULLS [NOT] DISTINCT.

### 3.4 Restricciones de integridad y valores nulos

**Restricciones inherentes al modelo:** no hay tuplas repetidas y los valores son atómicos.

**Restricciones de integridad:**

- **Integridad de dominio:** cada valor pertenece al dominio de su atributo (tipo, rango, CHECK).
- **Integridad de entidad:** ningún atributo de la clave primaria puede ser nulo.
- **Integridad referencial:** todo valor no nulo de una clave foránea debe existir en la clave referenciada. **(INAP 2022, clasificada en B3-T04: «si una tupla de R1 hace referencia a R2, debe referirse a una tupla que exista realmente en R2».)**
- **Reglas de negocio o semánticas:** restricciones propias de la organización, como «el importe no puede superar el crédito disponible». Se implementan con CHECK, aserciones o disparadores.

**Qué pasa al borrar o modificar una fila referenciada.** La clave foránea define una **acción referencial** para ON DELETE y ON UPDATE:

| Acción | Efecto al borrar la fila padre |
| --- | --- |
| RESTRICT | Impide el borrado y devuelve un error, comprobándolo de inmediato |
| NO ACTION | Impide el borrado, comprobándolo al final de la sentencia. Es la opción por defecto |
| CASCADE | Borra también las filas hijas |
| SET NULL | Pone a nulo la clave foránea de las hijas |
| SET DEFAULT | Pone el valor por defecto en la clave foránea de las hijas |

**INAP 2025 (clasificada en B3-T04).** Con ON DELETE RESTRICT, el SGBD **impide el borrado** de la fila padre y devuelve un error.

**Valores nulos.** NULL representa un valor **desconocido** o **no aplicable**. No es cero ni una cadena vacía. Introduce una **lógica de tres valores**: verdadero, falso y desconocido (apartado 4.8).

### 3.5 Las reglas de Codd

En 1985 Codd publicó las reglas que debe cumplir un SGBD para considerarse **plenamente relacional**. Se las llama «las 12 reglas», pero son **13 reglas**, numeradas del 0 al 12:

- **Regla 0 · Fundamental:** el sistema debe gestionar la base de datos exclusivamente con sus capacidades relacionales.
- **Regla 1 · Información:** toda la información se representa de una sola forma, como valores en tablas, incluidos los metadatos.
- **Regla 2 · Acceso garantizado:** cada dato es accesible sin ambigüedad mediante el **nombre de la tabla**, el **valor de la clave primaria** y el **nombre de la columna**.
- **Regla 3 · Tratamiento sistemático de los nulos:** los nulos se tratan de forma uniforme, independiente del tipo de datos.
- **Regla 4 · Catálogo dinámico en línea basado en el modelo relacional:** los metadatos se guardan en tablas y se consultan con el mismo lenguaje que los datos.
- **Regla 5 · Sublenguaje de datos completo:** al menos un lenguaje permite definir datos y vistas, manipular datos, definir restricciones de integridad, autorizar y gestionar transacciones.
- **Regla 6 · Actualización de vistas:** toda vista teóricamente actualizable debe poder actualizarse.
- **Regla 7 · Inserción, actualización y borrado de alto nivel:** las operaciones trabajan sobre conjuntos de filas, no solo sobre una.
- **Regla 8 · Independencia física de los datos.**
- **Regla 9 · Independencia lógica de los datos.**
- **Regla 10 · Independencia de la integridad:** las restricciones se definen en el lenguaje relacional y se guardan en el catálogo, no en los programas.
- **Regla 11 · Independencia de la distribución:** los usuarios no deben notar si los datos están distribuidos.
- **Regla 12 · No subversión:** si existe un lenguaje de bajo nivel, registro a registro, no puede usarse para saltarse las restricciones.

**INAP 2022.** Preguntó a qué regla corresponde «cualquier información debe ser accesible de manera unívoca mediante un nombre de tabla, un nombre de columna y el valor de la clave primaria». Es la **regla del acceso garantizado** (regla 2). Los distractores eran la regla fundamental (0), la de la información (1) y la de los nulos (3).

### 3.6 Álgebra relacional

El **álgebra relacional** es un lenguaje **procedimental** formado por operaciones que reciben relaciones y devuelven relaciones. Es un sistema **cerrado**: el resultado de una operación puede ser el operando de otra.

**Operaciones primitivas:**

| Operación | Símbolo | Qué hace | SQL equivalente |
| --- | --- | --- | --- |
| Selección | σ | Filas que cumplen una condición | SELECT * FROM R WHERE condición |
| Proyección | π | Solo algunas columnas, sin duplicados | SELECT DISTINCT a, b FROM R |
| Unión | ∪ | Filas de R, de S o de ambas | R UNION S |
| Diferencia | − | Filas de R que no están en S | R EXCEPT S |
| Producto cartesiano | × | Cada fila de R con cada fila de S | SELECT * FROM R CROSS JOIN S |
| Renombrado | ρ | Cambia el nombre de una relación o atributo | AS |

**Operaciones derivadas:**

| Operación | Símbolo | Qué hace | SQL equivalente |
| --- | --- | --- | --- |
| Intersección | ∩ | Filas que están en R y en S | R INTERSECT S |
| Combinación theta | ⋈θ | Producto cartesiano seguido de una selección | R JOIN S ON condición |
| Combinación natural | ⋈ | Iguala los atributos del mismo nombre y no los repite | R NATURAL JOIN S |
| División | ÷ | Valores de R relacionados con **todas** las filas de S | No existe; se expresa con NOT EXISTS anidados |

Unión, diferencia e intersección exigen relaciones **compatibles**: mismo grado y dominios compatibles.

**Diferencias con SQL:**

- La proyección del álgebra **elimina duplicados**; SELECT no lo hace si no se pone DISTINCT.
- MINUS es el nombre de la diferencia en Oracle; la norma usa EXCEPT.
- La división no tiene operador en SQL.

### 3.7 Cálculo relacional

El **cálculo relacional** es un lenguaje **declarativo** basado en la lógica de predicados: dice **qué** tuplas se quieren mediante una fórmula, con cuantificadores existencial (∃) y universal (∀).

- **Cálculo relacional de tuplas:** las variables representan tuplas. Es la base de SQL.
- **Cálculo relacional de dominios:** las variables representan valores de atributos. Es la base de QBE (*Query By Example*).

Codd demostró que el álgebra y el cálculo tienen la **misma capacidad expresiva**. Un lenguaje que puede expresar todo lo que expresa el álgebra se llama **relacionalmente completo**. SQL lo es y además añade agregación, ordenación y recursividad.

### 3.8 Normalización, en resumen

La **normalización** es el proceso de organizar las tablas para **reducir la redundancia** y evitar anomalías de inserción, borrado y modificación. **(INAP 2024, clasificada en B3-T04.)** Se basa en las dependencias funcionales: un atributo B depende funcionalmente de A (A → B) si cada valor de A determina un único valor de B.

- **1FN:** valores atómicos.
- **2FN:** 1FN y cada atributo no clave depende de la clave **completa**, no de una parte.
- **3FN:** 2FN y ningún atributo no clave depende **transitivamente** de la clave, es decir, a través de otro atributo no clave.
- **FNBC** (Boyce-Codd): todo determinante de una dependencia no trivial es clave candidata.
- **4FN y 5FN:** tratan las dependencias multivaluadas y de combinación.

A veces se **desnormaliza** a propósito para acelerar consultas, como en los almacenes de datos (B2-T04). El diseño y la normalización se estudian en B3-T04.

## 4. El lenguaje SQL

### 4.1 Características y sublenguajes

**SQL** (*Structured Query Language*) es el lenguaje normalizado de los SGBD relacionales. Nació en IBM a mediados de los años setenta como SEQUEL, para el prototipo System R, y es norma ANSI desde 1986 e ISO desde 1987 (apartado 7.2). Sus rasgos:

- **Declarativo:** se dice qué datos se quieren, no cómo obtenerlos.
- **Trabaja con conjuntos** de filas.
- **Completo:** un mismo lenguaje sirve para definir, manipular, controlar y gestionar transacciones (regla 5 de Codd).
- **Se usa de forma interactiva**, incrustado en un lenguaje anfitrión o mediante interfaces como ODBC y JDBC.

| Sublenguaje | Sentencias | Para qué |
| --- | --- | --- |
| DDL | CREATE, ALTER, DROP, TRUNCATE | Definir y modificar la estructura |
| DML | SELECT, INSERT, UPDATE, DELETE, MERGE | Consultar y modificar los datos |
| DCL | GRANT, REVOKE | Conceder y retirar privilegios |
| TCL | COMMIT, ROLLBACK, SAVEPOINT, SET TRANSACTION | Controlar las transacciones |

**INAP 2025.** Preguntó qué asociación es correcta. Lo era **«Create - DDL»**. Eran falsas «Select - DDL» (SELECT es DML), «Drop - DML» (DROP es DDL) e «Insert - DDL» (INSERT es DML).

La clasificación de algunas sentencias varía entre productos. TRUNCATE se considera DDL en casi todos ellos, y en Oracle y MySQL confirma la transacción en curso.

### 4.2 Tipos de datos

Tipos de datos de la norma:

- **Cadenas de caracteres:** CHAR(n), de longitud fija, que se rellena con espacios; VARCHAR(n), de longitud variable hasta n; NCHAR y NVARCHAR, para juegos de caracteres nacionales; CLOB, para textos grandes.
- **Números exactos:** SMALLINT, INTEGER, BIGINT, y NUMERIC(p, s) o DECIMAL(p, s), con p dígitos en total y s decimales. Son los adecuados para importes.
- **Números aproximados:** REAL, DOUBLE PRECISION, FLOAT. Tienen error de redondeo y no deben usarse para dinero.
- **Fecha y hora:** DATE, TIME, TIMESTAMP, con o sin zona horaria (WITH TIME ZONE), e INTERVAL.
- **Otros:** BOOLEAN, BINARY y VARBINARY, BLOB para binarios grandes, XML, JSON (tipo propio desde SQL:2023) y tipos definidos por el usuario.

Los productos añaden los suyos, como el VARCHAR2 de Oracle o el SERIAL de PostgreSQL.

### 4.3 Definición de datos

Ejemplo con dos tablas de un organismo:

- `CREATE TABLE unidad (id_unidad INTEGER PRIMARY KEY, nombre VARCHAR(100) NOT NULL UNIQUE, provincia CHAR(2));`
- `CREATE TABLE expediente (id_expediente INTEGER PRIMARY KEY, id_unidad INTEGER NOT NULL REFERENCES unidad (id_unidad) ON DELETE RESTRICT, fecha_entrada DATE NOT NULL, estado VARCHAR(20) DEFAULT 'ABIERTO' CHECK (estado IN ('ABIERTO', 'RESUELTO', 'ARCHIVADO')), importe DECIMAL(12,2));`

**Restricciones** (CONSTRAINT), en una columna o en la tabla:

- **NOT NULL:** la columna no admite nulos.
- **UNIQUE:** valores únicos.
- **PRIMARY KEY:** valores únicos y no nulos.
- **FOREIGN KEY ... REFERENCES:** clave foránea, con su acción referencial.
- **CHECK:** condición que debe cumplir cada fila.
- **DEFAULT:** valor por defecto.

Otras sentencias DDL:

- **ALTER TABLE:** añade, modifica o elimina columnas y restricciones. Por ejemplo, `ALTER TABLE expediente ADD COLUMN canal VARCHAR(10);`.
- **DROP TABLE:** elimina la tabla **con su definición**. Con CASCADE elimina también los objetos que dependen de ella.
- **CREATE INDEX:** crea un índice. No forma parte de la norma SQL, pero lo admiten todos los productos.
- **CREATE VIEW, CREATE SCHEMA, CREATE SEQUENCE y CREATE ROLE.** Las columnas autonuméricas se declaran con GENERATED AS IDENTITY.

### 4.4 Consultas: SELECT

Estructura completa:

- `SELECT [DISTINCT] columnas o expresiones`
- `FROM tablas y combinaciones`
- `WHERE condición sobre las filas`
- `GROUP BY columnas de agrupación`
- `HAVING condición sobre los grupos`
- `ORDER BY columnas [ASC | DESC]`
- `OFFSET n ROWS FETCH FIRST m ROWS ONLY`

El **orden lógico de evaluación** no es el de escritura:

1. FROM y JOIN.
2. WHERE.
3. GROUP BY.
4. HAVING.
5. SELECT.
6. DISTINCT.
7. ORDER BY.
8. OFFSET y FETCH.

Por eso **WHERE filtra filas antes de agrupar** y no puede usar funciones de agregado, mientras que **HAVING filtra grupos después de agrupar**. Y por eso un alias definido en SELECT no puede usarse en WHERE, pero sí en ORDER BY.

**Operadores de condición:**

- Comparación: =, <>, <, >, <=, >=.
- BETWEEN ... AND (intervalo, extremos incluidos).
- IN (lista o subconsulta).
- LIKE con comodines: % para cualquier secuencia y _ para un carácter.
- IS NULL e IS NOT NULL.
- AND, OR y NOT.

**Limitar el número de filas** es una de las mayores diferencias entre dialectos:

- La norma (SQL:2008) usa FETCH FIRST n ROWS ONLY.
- PostgreSQL y MySQL usan LIMIT.
- SQL Server usa TOP.
- Las versiones antiguas de Oracle usaban ROWNUM.

### 4.5 Combinaciones (joins)

- **INNER JOIN:** solo las filas con coincidencia en ambas tablas.
- **LEFT OUTER JOIN:** todas las filas de la tabla izquierda, con NULL en las columnas de la derecha cuando no hay coincidencia.
- **RIGHT OUTER JOIN:** el simétrico.
- **FULL OUTER JOIN:** todas las filas de ambas tablas.
- **CROSS JOIN:** producto cartesiano.
- **NATURAL JOIN:** combina por todas las columnas del mismo nombre. Es peligroso: si se añade una columna con un nombre repetido, cambia el resultado.
- **Autocombinación** (*self join*): una tabla combinada consigo misma con dos alias. Sirve, por ejemplo, para relacionar a un empleado con su jefe.

Ejemplo:

- `SELECT u.nombre, COUNT(e.id_expediente) AS total FROM unidad u LEFT JOIN expediente e ON e.id_unidad = u.id_unidad GROUP BY u.nombre;`

Devuelve **todas** las unidades, también las que no tienen expedientes, con total 0. Con INNER JOIN, esas unidades desaparecerían.

### 4.6 Agregación y agrupación

Las **funciones de agregado** devuelven un valor por grupo:

- COUNT, SUM, AVG, MIN y MAX.
- En la norma también existen otras, como LISTAGG o las estadísticas.

**Reglas:**

- Con GROUP BY, cada columna del SELECT que no está dentro de una función de agregado debe figurar en el GROUP BY.
- Las funciones de agregado **ignoran los nulos**. Por eso COUNT(*) cuenta filas y COUNT(columna) cuenta los valores **no nulos**. AVG divide entre los no nulos.

Ejemplo, unidades con más de 100 expedientes resueltos en 2026:

- `SELECT id_unidad, COUNT(*) FROM expediente WHERE estado = 'RESUELTO' AND fecha_entrada >= DATE '2026-01-01' GROUP BY id_unidad HAVING COUNT(*) > 100;`

Para análisis multidimensional existen GROUP BY ROLLUP, CUBE y GROUPING SETS (B2-T04).

### 4.7 Subconsultas, operadores de conjunto y otras construcciones

**Subconsultas:**

- **Escalares:** devuelven un solo valor.
- **De conjunto:** se usan con IN, ANY o SOME, y ALL.
- **Correlacionadas:** hacen referencia a la consulta exterior y se evalúan, conceptualmente, para cada fila de ella.
- **EXISTS / NOT EXISTS:** comprueban si la subconsulta devuelve alguna fila.

Ejemplo, unidades sin ningún expediente abierto:

- `SELECT nombre FROM unidad u WHERE NOT EXISTS (SELECT 1 FROM expediente e WHERE e.id_unidad = u.id_unidad AND e.estado = 'ABIERTO');`

**Trampa:** NOT IN con una subconsulta que devuelve algún NULL no devuelve ninguna fila, por la lógica de tres valores. NOT EXISTS no tiene ese problema.

**Operadores de conjunto:** combinan los resultados de dos consultas compatibles (mismo número de columnas y tipos compatibles):

- **UNION:** unión **sin** duplicados.
- **UNION ALL:** unión **con** duplicados. Es más rápida.
- **INTERSECT:** filas comunes a las dos consultas.
- **EXCEPT:** filas de la primera que no están en la segunda. Oracle lo llama MINUS.

**Otras construcciones:**

- **CASE:** expresión condicional dentro de una consulta.
- **COALESCE:** devuelve el primer valor no nulo.
- **Expresiones de tabla comunes** (CTE, cláusula WITH): subconsultas con nombre. Con **WITH RECURSIVE** (SQL:1999) permiten recorrer jerarquías, como un organigrama.
- **Funciones de ventana** (SQL:2003): calculan sobre un conjunto de filas relacionadas sin agruparlas. Por ejemplo, `ROW_NUMBER() OVER (PARTITION BY id_unidad ORDER BY fecha_entrada)` o una media móvil.

### 4.8 Los nulos en SQL

- Cualquier comparación con NULL da **desconocido**, incluso NULL = NULL. Por eso se usa IS NULL.
- WHERE solo deja pasar las filas cuya condición es **verdadera**; las desconocidas se descartan.
- Lógica de tres valores:
  - Falso AND desconocido = falso.
  - Verdadero OR desconocido = verdadero.
  - NOT desconocido = desconocido.
- Las funciones de agregado ignoran los nulos, salvo COUNT(*).
- Para agrupar y para DISTINCT, todos los nulos se tratan como un mismo grupo.

### 4.9 Modificación de datos

- **INSERT:** `INSERT INTO unidad (id_unidad, nombre, provincia) VALUES (7, 'Registro', '41');`, o INSERT ... SELECT para copiar filas de una consulta.
- **UPDATE:** `UPDATE expediente SET estado = 'ARCHIVADO' WHERE fecha_entrada < DATE '2020-01-01';`. Sin WHERE, modifica **todas** las filas.
- **DELETE:** `DELETE FROM expediente WHERE estado = 'ARCHIVADO';`. Sin WHERE, borra todas las filas, pero conserva la tabla.
- **MERGE** (SQL:2003): actualiza, inserta o borra filas de una tabla destino según coincidan o no con las de un origen. Es el *upsert*: WHEN MATCHED THEN UPDATE y WHEN NOT MATCHED THEN INSERT.

**DELETE, TRUNCATE y DROP:**

| | DELETE | TRUNCATE | DROP |
| --- | --- | --- | --- |
| Tipo | DML | DDL | DDL |
| Qué elimina | Las filas que cumplen el WHERE (o todas) | **Todas** las filas | La tabla entera, **con su definición** |
| Conserva la tabla | Sí | **Sí** | No |
| Admite WHERE | Sí | No | No |
| Disparadores de borrado | Se ejecutan | No se ejecutan | — |
| Velocidad | Lenta: registra cada fila | Rápida: libera las páginas | Rápida |
| Deshacer | ROLLBACK | Según el SGBD | Según el SGBD |

**INAP 2019.** Preguntó qué comando SQL elimina el contenido completo de una tabla sin eliminar la tabla. La respuesta era **TRUNCATE**. DROP elimina también la tabla, ALTER modifica su estructura y ERASE no existe en SQL. TRUNCATE TABLE se incorporó a la norma en SQL:2008.

### 4.10 Vistas

Una **vista** es una **tabla virtual** definida por una consulta con nombre. Solo se guarda su definición, y el SGBD la sustituye en cada consulta que la usa. Ejemplo:

- `CREATE VIEW pendientes AS SELECT id_expediente, id_unidad, fecha_entrada FROM expediente WHERE estado = 'ABIERTO';`

Para qué sirven:

- **Implementar el nivel externo** de ANSI/SPARC: cada usuario ve su parte.
- **Seguridad:** se concede acceso a la vista y no a la tabla.
- **Independencia lógica:** si cambia la tabla, se redefine la vista.
- **Simplificar** consultas complejas.

**Vistas actualizables.** Una vista admite INSERT, UPDATE o DELETE si cada fila de la vista corresponde a una sola fila de una tabla base: sin agregados, sin DISTINCT ni GROUP BY, y normalmente sobre una sola tabla. WITH CHECK OPTION impide insertar o modificar filas que luego no se verían en la vista. Para vistas no actualizables se pueden usar disparadores INSTEAD OF.

**Vista materializada:** guarda físicamente el resultado de la consulta como una tabla y se **refresca** periódicamente o al cambiar los datos. Acelera las consultas a costa de espacio y de posibles datos desfasados. No forma parte de la norma SQL.

### 4.11 Control de acceso

- **GRANT** concede privilegios: `GRANT SELECT, UPDATE ON expediente TO tramitador;`.
- **REVOKE** los retira: `REVOKE UPDATE ON expediente FROM tramitador;`.
- **Privilegios:**
  - Sobre objetos: SELECT, INSERT, UPDATE (incluso por columnas), DELETE, REFERENCES y EXECUTE.
  - De sistema, según el producto: crear tablas o usuarios, por ejemplo.
- **WITH GRANT OPTION:** permite a quien recibe el privilegio concederlo a otros. Al revocarlo con CASCADE, se retira también a quienes lo recibieron de él.
- **Roles:** conjuntos de privilegios que se asignan a usuarios (CREATE ROLE). Facilitan aplicar el **mínimo privilegio**.

### 4.12 SQL procedimental, incrustado y dinámico

SQL estándar no tiene bucles ni variables. Para escribir lógica dentro del SGBD se usan extensiones procedimentales:

- **SQL/PSM** (*Persistent Stored Modules*): la parte de la norma para procedimientos y funciones.
- Dialectos de los productos: **PL/SQL** (Oracle), **Transact-SQL** (SQL Server), **PL/pgSQL** (PostgreSQL) y **SQL PL** (Db2).

Con ellas se crean:

- **Procedimientos almacenados:** bloques de código que se ejecutan en el servidor con CALL o EXECUTE. Reducen el tráfico de red y centralizan la lógica.
- **Funciones:** devuelven un valor y se pueden usar dentro de las consultas.
- **Disparadores** (*triggers*): código que se ejecuta **automáticamente** ante un evento (INSERT, UPDATE o DELETE) sobre una tabla.
  - Se ejecutan **antes** o **después** del evento (BEFORE o AFTER), o **en lugar de** él (INSTEAD OF, en vistas).
  - Pueden ejecutarse una vez **por cada fila** afectada o una vez **por sentencia**.
  - Sirven para reglas de negocio complejas, auditoría y datos derivados. Se incorporaron a la norma en SQL:1999.
- **Cursores:** recorren fila a fila el resultado de una consulta desde un programa (DECLARE, OPEN, FETCH, CLOSE).

**SQL incrustado** (*embedded SQL*): sentencias SQL escritas dentro de un programa en otro lenguaje (C, COBOL), marcadas con EXEC SQL. Un **precompilador** las sustituye por llamadas a la biblioteca del SGBD antes de compilar el programa.

**SQL dinámico:** la sentencia se construye y se prepara **en tiempo de ejecución** (PREPARE y EXECUTE). Las interfaces ODBC y JDBC funcionan así.

**Inyección SQL.** Construir una sentencia concatenando datos del usuario permite a un atacante modificarla. La defensa principal son las **consultas parametrizadas**: la sentencia se prepara con marcadores (?) y los valores se enlazan aparte (PreparedStatement en JDBC), de modo que el SGBD nunca los interpreta como SQL. Se completa con el mínimo privilegio de la cuenta de la aplicación y con la validación de las entradas.

## 5. Transacciones, concurrencia y recuperación

### 5.1 Transacción y propiedades ACID

Una **transacción** es una **unidad lógica de trabajo**: un conjunto de operaciones que deben ejecutarse como un todo. El ejemplo clásico es una transferencia: cargo en una cuenta y abono en otra. Debe cumplir las propiedades **ACID**:

- **Atomicidad** (*Atomicity*): se ejecutan **todas** las operaciones o **ninguna**. Si algo falla, se deshace lo hecho. Se garantiza con **COMMIT y ROLLBACK** y el registro de transacciones.
- **Consistencia** (*Consistency*): la transacción lleva la base de datos de un estado válido a otro estado válido, respetando todas las restricciones.
- **Aislamiento** (*Isolation*): las transacciones concurrentes no interfieren entre sí. El resultado es el mismo que si se hubieran ejecutado una tras otra, o el que permita el nivel de aislamiento elegido.
- **Durabilidad o persistencia** (*Durability*): una vez confirmada, la transacción permanece aunque falle el sistema.

**INAP 2022 (clasificada en B3-T04).** ACID significa **atomicidad, consistencia, aislamiento y durabilidad o persistencia**. Los distractores cambiaban el aislamiento por «integridad» o mezclaban la tríada de seguridad CIA.

**INAP 2019 (clasificada en B3-T04).** La propiedad que hace que los resultados de una transacción se completen todos o se deshagan todos se asocia con **Commit - Rollback - Atomicidad**.

### 5.2 Control de transacciones en SQL

- **START TRANSACTION** o BEGIN: inicio explícito. En la norma, la transacción empieza implícitamente con la primera sentencia.
- **COMMIT:** confirma y hace permanentes los cambios.
- **ROLLBACK:** deshace todos los cambios desde el inicio de la transacción.
- **SAVEPOINT nombre** y **ROLLBACK TO SAVEPOINT nombre:** deshace solo hasta un punto intermedio.
- **SET TRANSACTION ISOLATION LEVEL:** fija el nivel de aislamiento.
- **Autocommit:** muchas herramientas e interfaces confirman cada sentencia automáticamente si no se abre una transacción explícita.

### 5.3 Anomalías de concurrencia

Cuando varias transacciones se ejecutan a la vez sin control suficiente aparecen estas anomalías:

- **Actualización perdida** (*lost update*): T1 y T2 leen el mismo saldo, ambas lo modifican y la escritura de T2 sobrescribe la de T1.
- **Lectura sucia** (*dirty read*): T1 lee un dato modificado por T2 que **todavía no se ha confirmado**. Si T2 hace ROLLBACK, T1 ha usado un valor que nunca existió. **(INAP 2025, clasificada en B3-T04.)**
- **Lectura no repetible** (*non-repeatable read*): T1 lee una fila dos veces y obtiene valores distintos porque T2 la **modificó o borró** y confirmó entre ambas lecturas.
- **Lectura fantasma** (*phantom read*): T1 repite una consulta **por condición** y aparecen o desaparecen filas porque T2 **insertó o borró** filas que cumplen la condición.

### 5.4 Niveles de aislamiento

La norma SQL define cuatro niveles según qué anomalías permiten:

| Nivel | Lectura sucia | Lectura no repetible | Lectura fantasma |
| --- | --- | --- | --- |
| READ UNCOMMITTED | Posible | Posible | Posible |
| READ COMMITTED | **Evitada** | Posible | Posible |
| REPEATABLE READ | Evitada | **Evitada** | Posible |
| SERIALIZABLE | Evitada | Evitada | **Evitada** |

A más aislamiento, menos anomalías pero menos concurrencia. El nivel por defecto es READ COMMITTED en Oracle, PostgreSQL y SQL Server, y REPEATABLE READ en MySQL con InnoDB. Los productos implementan los niveles de forma distinta: con MVCC, REPEATABLE READ de PostgreSQL ya evita los fantasmas, y el SERIALIZABLE de Oracle es en realidad **aislamiento por instantánea** (*snapshot isolation*).

**INAP 2019 (clasificada en B3-T04).** Con READ COMMITTED **no se producen lecturas sucias, pero pueden producirse lecturas no repetibles y fantasma**.

### 5.5 Técnicas de control de concurrencia

**Bloqueos** (*locks*):

- **Compartido** (S, de lectura): varias transacciones pueden tenerlo a la vez sobre el mismo dato.
- **Exclusivo** (X, de escritura): incompatible con cualquier otro.
- **Granularidad:** fila, página, tabla o base de datos. A menor granularidad, más concurrencia y más coste de gestión. Algunos SGBD **escalan** muchos bloqueos de fila a uno de tabla.

**Bloqueo en dos fases** (2PL, *two-phase locking*): cada transacción tiene una **fase de crecimiento**, en la que adquiere bloqueos, y una **fase de decrecimiento**, en la que los libera. Tras liberar el primero, ya no puede adquirir ninguno. Garantiza la **serializabilidad**. Variantes:

- **2PL básico:** solo cumple la regla de las dos fases. Puede producir lecturas sucias y abortos en cascada.
- **2PL estricto:** mantiene los bloqueos **exclusivos** hasta el COMMIT o ROLLBACK. Evita los abortos en cascada.
- **2PL riguroso:** mantiene **todos** los bloqueos hasta el final.

**Control multiversión** (MVCC, *Multi-Version Concurrency Control*): cada escritura crea una nueva versión del dato y cada lectura ve una **instantánea** coherente. Las lecturas no bloquean a las escrituras ni al revés. Lo usan Oracle, PostgreSQL, el motor InnoDB de MySQL y SQL Server (opcional).

**Otras técnicas:**

- **Ordenación por marcas de tiempo** (*timestamps*): las operaciones conflictivas se ejecutan en el orden de inicio de las transacciones.
- **Control optimista:** no bloquea. Al confirmar, comprueba si hubo conflicto y, si lo hubo, aborta. Es adecuado cuando los conflictos son raros.

### 5.6 Interbloqueos

Un **interbloqueo** (*deadlock*) ocurre cuando T1 espera un recurso bloqueado por T2 y T2 espera otro bloqueado por T1. Ninguna puede avanzar. El SGBD:

- **Lo detecta:** busca ciclos en el **grafo de espera** y aborta una transacción, la «víctima», que la aplicación debe reintentar. Es lo habitual.
- **Lo previene:** ordena el acceso a los recursos o usa esquemas basados en marcas de tiempo, como *wait-die* y *wound-wait*.
- **Usa tiempos de espera máximos** (*timeouts*).

### 5.7 Recuperación

La recuperación garantiza la **atomicidad** y la **durabilidad** frente a fallos de la transacción, del sistema o del disco.

- **Registro de transacciones** (*log* o diario): guarda cada cambio con el valor anterior y el nuevo. Con el valor anterior se puede deshacer y con el nuevo se puede rehacer.
- **Registro previo a la escritura** (WAL, *Write-Ahead Logging*): el registro de un cambio se escribe en disco **antes** que el propio dato. El COMMIT solo termina cuando su registro está en disco.
- **Tras una caída:**
  - **REDO (rehacer):** las transacciones confirmadas cuyos datos no llegaron a disco.
  - **UNDO (deshacer):** las no confirmadas cuyos cambios sí llegaron.

  El algoritmo de referencia es ARIES (IBM).
- **Puntos de control** (*checkpoints*): vuelcan a disco las páginas modificadas para que la recuperación no tenga que recorrer todo el registro.
- **Fallo del soporte:** se restaura la **copia de seguridad** y se aplica el registro archivado hasta el momento deseado (B4-T02).

### 5.8 Transacciones distribuidas, CAP y BASE

Cuando una transacción modifica datos en **varios SGBD**, se coordina con el **protocolo de confirmación en dos fases** (2PC, *two-phase commit*):

1. **Preparación:** el coordinador pregunta a cada participante si puede confirmar. Cada uno deja sus cambios listos y responde.
2. **Confirmación:** si todos responden que sí, el coordinador ordena el COMMIT; si alguno responde que no, el ROLLBACK.

Lo estandariza **X/Open XA** (apartado 7.8).

**Teorema CAP** (Brewer, 2000; demostrado por Gilbert y Lynch en 2002). Un sistema de datos **distribuido** no puede garantizar a la vez:

- **Consistencia:** todas las lecturas ven la última escritura.
- **Disponibilidad:** toda petición recibe respuesta.
- **Tolerancia a particiones:** el sistema sigue funcionando aunque se corte la comunicación entre nodos.

Como las particiones de red no se pueden descartar, cuando ocurren hay que elegir entre consistencia y disponibilidad. **La «C» de CAP no es la de ACID**, y CAP no afecta a un SGBD relacional de un solo nodo.

**BASE** (*Basically Available, Soft state, Eventual consistency*) es el enfoque de muchas bases NoSQL: priorizan la disponibilidad y aceptan una consistencia **eventual**. **(INAP 2019, clasificada en B3-T15: BASE es el principio común de las bases de datos NoSQL.)**

## 6. Arquitectura interna del SGBD

### 6.1 Componentes

La descripción más citada (Silberschatz, Korth y Sudarshan) divide el SGBD en dos grandes módulos.

**Procesador de consultas:**

- **Intérprete DDL:** procesa las sentencias de definición y guarda las definiciones en el diccionario.
- **Compilador DML:** traduce las sentencias DML a un plan de ejecución de bajo nivel, eligiendo el más eficiente (**optimización**).
- **Precompilador DML:** convierte el SQL incrustado en un programa anfitrión en llamadas a procedimientos (apartado 4.12).
- **Motor de evaluación o de ejecución de consultas:** ejecuta las instrucciones de bajo nivel generadas por el compilador.

**Gestor de almacenamiento:**

- **Gestor de autorización e integridad:** comprueba los permisos y las restricciones.
- **Gestor de transacciones:** garantiza ACID, incluido el control de concurrencia.
- **Gestor de archivos:** reserva el espacio en disco y gestiona las estructuras de datos.
- **Gestor de memoria intermedia** (*buffer*): trae las páginas del disco a memoria y decide cuáles mantener.

**Estructuras de datos en disco:** ficheros de datos, diccionario de datos, índices y, en la descripción más habitual, el registro de transacciones.

**INAP 2022.** Preguntó por los **componentes de proceso** de un SGBD. La respuesta era **«compilador DML, precompilador DML, intérprete DDL y motor de ejecución»**, que son los del procesador de consultas. Los distractores mezclaban componentes del gestor de almacenamiento (gestor de ficheros, gestor de transacciones) o conceptos ajenos (estructuras de datos, modelo de referencia).

### 6.2 Componentes según el flujo de una transacción

Otra descripción clásica, la de las fuentes de oposición, sigue el camino de una transacción:

- **Procesador de consultas:** analiza la sentencia con ayuda del diccionario, la optimiza y la convierte en operaciones elementales (leer, escribir, confirmar, deshacer).
- **Gestor de transacciones:** recibe las operaciones de las transacciones concurrentes.
- **Planificador** (*scheduler*): decide en qué orden se ejecutan para que el resultado sea correcto. Si usa bloqueos, se llama **gestor de bloqueos** (*lock manager*).
- **Gestor de datos:**
  - **Gestor de recuperación:** ejecuta COMMIT y ROLLBACK y garantiza la atomicidad y la durabilidad.
  - **Gestor de memoria intermedia:** ejecuta las lecturas y escrituras.

### 6.3 Procesamiento y optimización de consultas

1. **Análisis:** se comprueba la sintaxis y, con el diccionario, que existen las tablas y columnas y que el usuario tiene permisos.
2. **Reescritura:** se sustituyen las vistas por su definición y se simplifican las condiciones.
3. **Optimización:** el **optimizador basado en costes** genera planes alternativos y estima el coste de cada uno con las **estadísticas**: número de filas, distribución de valores e índices disponibles. Elige:
   - El orden de las combinaciones.
   - El método de acceso: recorrido completo o por índice.
   - El algoritmo de combinación: bucles anidados (*nested loops*), por *hash* (*hash join*) o por ordenación y mezcla (*sort-merge join*).
4. **Ejecución** del plan elegido. EXPLAIN muestra el plan.

Problemas típicos de rendimiento:

- Estadísticas desactualizadas.
- Falta de índices o índices inútiles.
- Funciones aplicadas a columnas indexadas, que impiden usar el índice.
- Consultas N+1 desde la aplicación.
- Recorridos completos de tablas grandes.

### 6.4 Índices

Un **índice** es una estructura auxiliar que permite localizar filas sin recorrer toda la tabla, como el índice de un libro. **Acelera las lecturas** por las columnas indexadas, pero **ocupa espacio** y **penaliza las escrituras**, porque cada INSERT, UPDATE o DELETE debe actualizarlo.

- **Árbol B+:** el tipo por defecto. Sirve para igualdad, rangos y ordenación.
- **Hash:** muy rápido para igualdad, inútil para rangos.
- **Bitmap:** adecuado para columnas con pocos valores distintos y en almacenes de datos (B2-T04). Muy costoso con muchas escrituras.
- **Agrupado** (*clustered*): las filas de la tabla se guardan **ordenadas** según el índice. Solo puede haber uno por tabla.
- **No agrupado:** estructura separada con punteros a las filas.
- **Compuesto:** sobre varias columnas. Solo se aprovecha si la consulta usa las primeras columnas (prefijo izquierdo).
- **Único:** garantiza la unicidad. Las claves primarias y las restricciones UNIQUE suelen crear uno.
- **De cobertura:** contiene todas las columnas que necesita la consulta, que no tiene que leer la tabla.

La **selectividad** es la proporción de filas que devuelve una condición. Un índice es útil cuando la condición es selectiva, es decir, cuando devuelve pocas filas.

## 7. Normas y estándares para la interoperabilidad

### 7.1 Por qué hace falta

La **interoperabilidad** entre SGBD relacionales es la capacidad de que aplicaciones, herramientas y gestores de distintos fabricantes trabajen juntos. Se apoya en tres niveles de estándares:

- **Un lenguaje común:** la norma SQL.
- **Interfaces de programación comunes** para conectarse y ejecutar SQL: SQL/CLI, ODBC, JDBC, ADO.NET y PDO.
- **Protocolos para transacciones y acceso distribuidos:** XA, DRDA y SQL/MED.

Ninguno elimina del todo las diferencias: cada producto tiene su **dialecto** con extensiones. La portabilidad real exige ceñirse a la norma y aislar lo específico.

### 7.2 La norma SQL

SQL es norma **ANSI** (X3.135) desde 1986 e **ISO/IEC 9075** desde 1987. La edición vigente es **SQL:2023**.

| Versión | Novedades principales |
| --- | --- |
| SQL-86 / SQL-87 | Primera norma |
| SQL-89 | Restricciones de integridad básicas |
| **SQL-92 (SQL2)** | Gran ampliación: JOIN explícito, CASE, nuevos tipos, niveles de aislamiento, INFORMATION_SCHEMA. Tres niveles de conformidad: inicial, intermedio y completo |
| **SQL:1999 (SQL3)** | Consultas recursivas (WITH RECURSIVE), disparadores, tipo BOOLEAN, expresiones regulares, características objeto-relacionales |
| SQL:2003 | SQL/XML, funciones de ventana, MERGE, secuencias y columnas de identidad |
| SQL:2006 | Integración con XQuery |
| SQL:2008 | TRUNCATE TABLE, disparadores INSTEAD OF, FETCH FIRST |
| SQL:2011 | Datos temporales: tablas con periodos de validez e historial |
| SQL:2016 | JSON, reconocimiento de patrones en filas, LISTAGG |
| SQL:2019 | Matrices multidimensionales (SQL/MDA) |
| **SQL:2023** | Tipo de datos JSON y consultas de grafos de propiedades (SQL/PGQ) |

Desde SQL:1999 la conformidad se mide frente a un **núcleo** (*Core SQL*) obligatorio y un conjunto de características opcionales. Ningún producto implementa toda la norma.

En 2024 ISO publicó **GQL** (ISO/IEC 39075), un lenguaje de consulta para bases de datos de grafos. Es la primera norma de lenguaje de bases de datos nueva desde SQL.

| 16 | PGQ | Consultas sobre grafos de propiedades |

### 7.4 SQL/CLI y ODBC

Una **interfaz de nivel de llamada** (CLI, *Call-Level Interface*) es una biblioteca de funciones que la aplicación invoca para conectarse a un SGBD, enviar sentencias SQL como cadenas y recoger los resultados. No necesita precompilador. Hay dos normas de referencia: **X/Open CLI** e **ISO SQL/CLI**, la parte 3 de la norma.

**ODBC** (*Open Database Connectivity*) es la implementación de Microsoft (1992), basada en esas normas y disponible en Windows, Linux y macOS. Su arquitectura tiene cuatro capas:

1. **Aplicación:** llama a las funciones ODBC.
2. **Gestor de drivers** (*Driver Manager*): carga el driver adecuado.
3. **Driver:** traduce las llamadas al protocolo y al dialecto del SGBD concreto. Lo suele proporcionar el fabricante.
4. **Fuente de datos:** el SGBD, identificado por un **DSN** (*Data Source Name*) o por una cadena de conexión.

La misma aplicación puede trabajar con cualquier SGBD que tenga driver ODBC.

### 7.5 JDBC

**JDBC** (*Java Database Connectivity*) es la API estándar de **Java** para acceder a bases de datos relacionales (Sun, 1997). Está en los paquetes java.sql y javax.sql. Sus interfaces principales son:

- **DriverManager y DataSource:** obtienen la conexión.
- **Connection:** la conexión, con commit, rollback y el nivel de aislamiento.
- **Statement, PreparedStatement y CallableStatement:** ejecutan sentencias, sentencias preparadas con parámetros y procedimientos almacenados.
- **ResultSet:** recorre los resultados.

**Tipos de driver JDBC:**

| Tipo | Nombre | Funcionamiento |
| --- | --- | --- |
| 1 | Puente JDBC-ODBC | Traduce las llamadas JDBC a ODBC. Se eliminó en Java 8 |
| 2 | API nativa, parcialmente Java | Llama a la biblioteca nativa del SGBD, que debe estar instalada en el cliente |
| 3 | Protocolo de red, *middleware* | Driver Java puro que habla con un servidor intermedio, y este con el SGBD |
| 4 | Protocolo nativo, Java puro | Driver Java puro que habla directamente el protocolo del SGBD. Es el más usado y el de mejor rendimiento |

Sobre JDBC trabajan **JPA** (*Jakarta Persistence*, antes *Java Persistence API*), con su lenguaje JPQL, y sus implementaciones, como **Hibernate** o EclipseLink (B3-T10).

### 7.6 Tecnologías de Microsoft y de otros lenguajes

- **OLE DB:** interfaz de Microsoft basada en COM (1996) para acceder a fuentes de datos relacionales y no relacionales. Microsoft anunció su retirada para SQL Server en 2011, pero la revirtió en 2017 con un nuevo proveedor (MSOLEDBSQL).
- **ADO** (*ActiveX Data Objects*): capa de objetos sobre OLE DB para las aplicaciones COM clásicas.
- **ADO.NET:** la tecnología de acceso a datos de **.NET** (B3-T11).
  - Cada SGBD aporta un **proveedor de datos**, como SqlClient para SQL Server.
  - Sus objetos principales son Connection, Command, DataReader (lectura rápida hacia delante) y DataSet (datos en memoria, trabajo **desconectado**).
  - Sobre ADO.NET trabaja **Entity Framework**, el ORM de Microsoft.
- **PHP:** **PDO** (*PHP Data Objects*) ofrece una interfaz común con drivers para los SGBD habituales.
- **Python:** la especificación **DB-API 2.0** (PEP 249) define una interfaz común que siguen los drivers de cada SGBD.

### 7.7 Mapeo objeto-relacional (ORM)

Un **ORM** (*Object-Relational Mapping*) traduce entre los **objetos** de un lenguaje orientado a objetos y las **tablas** de una base de datos relacional. Así el programador trabaja con clases y el ORM genera el SQL. Resuelve el **desajuste de impedancia** objeto-relacional: herencia, colecciones e identidad frente a tablas, filas y claves. Ejemplos:

- **Java:** Hibernate y otras implementaciones de JPA, y MyBatis (antes iBatis), que mapea sentencias SQL.
- **.NET:** Entity Framework y NHibernate.
- **PHP:** Doctrine y Eloquent.
- **Python:** SQLAlchemy y el ORM de Django.

**Ventajas:** productividad y cierta **portabilidad** entre SGBD, porque el ORM genera el dialecto de cada uno. **Inconvenientes:** consultas ineficientes si no se controla (el problema N+1) y pérdida de las funciones específicas del SGBD.

### 7.8 Transacciones distribuidas y acceso remoto

- **X/Open XA** (*eXtended Architecture*, modelo DTP de The Open Group, 1991): define la interfaz entre un **gestor de transacciones** y los **gestores de recursos** (SGBD, colas de mensajes) para coordinar una transacción global con **confirmación en dos fases**. En Java lo usa **JTA** (*Jakarta Transactions*).
- **DRDA** (*Distributed Relational Database Architecture*): protocolo de IBM, adoptado por The Open Group, para acceder a bases de datos relacionales remotas. Lo usa Db2.
- **SQL/MED** y mecanismos equivalentes: permiten consultar desde un SGBD tablas de otro como si fueran locales. Ejemplos: los *foreign data wrappers* de PostgreSQL, los *database links* de Oracle y los servidores vinculados de SQL Server.

### 7.9 Intercambio de datos y portabilidad

Cuando no basta con conectarse, sino que hay que **mover** datos entre gestores:

- **Formatos de intercambio:** CSV, XML (SQL/XML), JSON y formatos columnares como Parquet. Sirven para intercambiar datos, pero no ofrecen interoperabilidad transaccional.
- **ETL o ELT, replicación y captura de cambios** (CDC): sincronizan datos entre plataformas (B2-T04).
- **Herramientas de migración** de esquemas y datos entre productos.

**Diferencias de dialecto que rompen la portabilidad:**

| Necesidad | Norma SQL | Variantes de los productos |
| --- | --- | --- |
| Limitar filas | FETCH FIRST n ROWS ONLY | LIMIT (PostgreSQL, MySQL), TOP (SQL Server), ROWNUM (Oracle antiguo) |
| Diferencia de consultas | EXCEPT | MINUS (Oracle) |
| Autonumérico | GENERATED AS IDENTITY | AUTO_INCREMENT (MySQL), SERIAL (PostgreSQL), IDENTITY (SQL Server) |
| Lenguaje procedimental | SQL/PSM | PL/SQL, Transact-SQL, PL/pgSQL, SQL PL |
| Cadenas de texto | VARCHAR | VARCHAR2 (Oracle) |

**Buenas prácticas de portabilidad:**

- Usar SQL de la norma y tipos estándar.
- Encapsular lo específico del producto.
- Acceder mediante interfaces estándar (ODBC, JDBC) o un ORM.
- Publicar los datos mediante **servicios o API** en lugar de dar acceso directo a la base de datos.
- Documentar codificación de caracteres, zonas horarias y formatos de fecha.

En la Administración, el **Esquema Nacional de Interoperabilidad** pide usar estándares abiertos (B1-T09).

## 8. Seguridad de las bases de datos

- **Mínimo privilegio:**
  - Cuentas separadas para las aplicaciones, los administradores y las personas.
  - Roles.
  - Sin cuentas genéricas compartidas.
- **Autenticación robusta**, integrada con el directorio corporativo cuando es posible.
- **Cifrado:**
  - **En tránsito:** TLS entre la aplicación y el SGBD.
  - **En reposo:** cifrado transparente de ficheros (TDE) y de copias de seguridad.
  - **Por columna** para los datos más sensibles.
- **Auditoría** de accesos y cambios, especialmente los de los administradores.
- **Enmascaramiento** y seudonimización en los entornos de prueba.
- **Defensa frente a la inyección SQL:** consultas parametrizadas (apartado 4.12).
- **Bastionado y parcheo** del SGBD, y **copias de seguridad probadas** (B4-T02).
- En la Administración, todo ello conforme al **ENS** y al RGPD (B1-T07).

## 10. Aplicación al supuesto práctico

En un supuesto, la base de datos aparece al diseñar un sistema de gestión nuevo, al migrar uno existente o al integrar varios. Conviene:

1. **Elegir el tipo de SGBD por requisitos.** Relacional si hay transacciones, integridad entre entidades y consultas variadas, que es el caso habitual en la gestión administrativa. NoSQL solo si el volumen, el esquema variable o la escala lo justifican (B3-T15).
2. **Elegir el producto con criterios explícitos:** soporte, licencias y coste total (libre como PostgreSQL o MariaDB, o comercial), competencias del equipo, alta disponibilidad, despliegue en local o en la nube, y cumplimiento del ENS.
3. **Diseñar el esquema:**
   - Tablas normalizadas hasta 3FN (B3-T04).
   - Claves primarias y foráneas con su acción referencial.
   - Restricciones CHECK y NOT NULL para que la integridad la garantice el SGBD y no solo la aplicación.
4. **Usar la arquitectura ANSI/SPARC:**
   - **Vistas** por perfil de usuario (nivel externo) y privilegios sobre ellas.
   - **Índices** según las consultas frecuentes (nivel interno), sin tocar las aplicaciones.
5. **Definir las transacciones críticas** y su **nivel de aislamiento**. Por ejemplo, el registro de un pago necesita atomicidad y evitar actualizaciones perdidas.
6. **Garantizar la interoperabilidad:**
   - SQL de la norma.
   - Acceso por JDBC u ODBC con un *pool* de conexiones, o mediante un ORM.
   - Exposición de los datos a otros sistemas mediante servicios o API, no con acceso directo a las tablas.
   - Formatos abiertos para el intercambio.
7. **Seguridad y continuidad:**
   - Cuentas con mínimo privilegio y consultas parametrizadas.
   - Cifrado y auditoría.
   - Copias con restauración probada y réplicas (B4-T02).
8. **En una migración entre productos:**
   - Inventariar las dependencias del dialecto (procedimientos, tipos, funciones).
   - Convertir el esquema, migrar y validar los datos.
   - Probar el rendimiento.
   - Prever la vuelta atrás.

## Resumen de repaso

### Núcleo de estudio

- **Base de datos:** datos persistentes, estructurados e interrelacionados, compartidos. **SGBD:** software que permite definirlos, consultarlos y modificarlos garantizando independencia, integridad, concurrencia, recuperación y seguridad. El **diccionario de datos** guarda los metadatos; es activo en los SGBD relacionales (INFORMATION_SCHEMA).
- **ANSI/SPARC (1975–1978):** tres niveles, cada uno con su esquema:
  - **Externo:** vistas; puede haber varios.
  - **Conceptual:** esquema lógico global; uno solo.
  - **Interno:** almacenamiento; uno solo.

  Dos correspondencias dan dos **independencias**: la **física** (cambiar el interno sin tocar el conceptual) y la **lógica** (cambiar el conceptual sin tocar los externos), que es más difícil.
- **Modelo relacional (Codd, 1970):** relaciones, tuplas, atributos y dominios. Grado = número de atributos; cardinalidad = número de tuplas. Sin tuplas duplicadas, sin orden y con valores atómicos.
- **Claves:** superclave, candidata (mínima), primaria (sin nulos, una por tabla), alternativa (UNIQUE) y foránea.
- **Integridad:** de dominio, de entidad (clave primaria sin nulos) y referencial (la clave foránea existe en la referenciada), con las acciones CASCADE, SET NULL, SET DEFAULT, RESTRICT y NO ACTION.
- **Reglas de Codd:** 13, del 0 al 12. La 2 es la del **acceso garantizado** (tabla, clave primaria y columna).
- **Álgebra relacional:** primitivas σ, π, ∪, −, × y ρ; derivadas ∩, combinaciones y ÷. El cálculo relacional es declarativo y equivalente en potencia.
- **SQL:** declarativo y relacionalmente completo. Sublenguajes:
  - DDL: CREATE, ALTER, DROP y TRUNCATE.
  - DML: SELECT, INSERT, UPDATE, DELETE y MERGE.
  - DCL: GRANT y REVOKE.
  - TCL: COMMIT, ROLLBACK y SAVEPOINT.
- **Consultas:** orden lógico FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Combinaciones INNER, LEFT, RIGHT, FULL y CROSS. Subconsultas con IN, EXISTS, ANY y ALL. UNION, INTERSECT y EXCEPT. CTE y funciones de ventana. Los nulos dan lógica de tres valores.
- **Vistas** (nivel externo, seguridad, independencia lógica) e **índices** (árbol B+, *hash*, *bitmap*, agrupado): aceleran lecturas y penalizan escrituras.
- **Transacciones ACID** con COMMIT y ROLLBACK. Anomalías: actualización perdida, lectura sucia, no repetible y fantasma. Cuatro niveles de aislamiento. Control con 2PL (básico, estricto, riguroso), MVCC u optimista. Interbloqueos detectados con el grafo de espera. Recuperación con registro WAL, UNDO/REDO y puntos de control. 2PC para transacciones distribuidas. CAP y BASE para sistemas distribuidos.
- **Componentes del SGBD:**
  - **Procesador de consultas:** intérprete DDL, compilador DML, precompilador DML y motor de ejecución.
  - **Gestor de almacenamiento:** autorización e integridad, transacciones, archivos y memoria intermedia.

  El optimizador basado en costes usa estadísticas.
- **Interoperabilidad:**
  - Norma SQL (ISO/IEC 9075; vigente SQL:2023; hitos SQL-92 y SQL:1999).
  - SQL/CLI y ODBC (aplicación, gestor de drivers, driver, fuente de datos).
  - JDBC con cuatro tipos de driver (el 4, Java puro, es el habitual).
  - OLE DB, ADO y ADO.NET; PDO; DB-API.
  - ORM (JPA/Hibernate, Entity Framework).
  - XA y 2PC, DRDA, SQL/MED.
  - Formatos de intercambio, replicación y CDC.

### Claves de test

- Niveles ANSI/SPARC: **externo, conceptual e interno**. El externo no es el «lógico». No confundir con «lógico, conceptual y físico» ni con MVC.
- Independencia física = cambiar el nivel interno. Independencia lógica = cambiar el conceptual. Poder cambiar un nivel sin tocar el superior = **independencia de datos**.
- Esquemas: varios externos, un conceptual y un interno.
- Componentes de proceso del SGBD: **compilador DML, precompilador DML, intérprete DDL y motor de ejecución**. El gestor de ficheros y el de transacciones son del gestor de almacenamiento.
- Reglas de Codd: 13 (0–12). 0 fundamental, 1 información, **2 acceso garantizado** (tabla + clave primaria + columna), 3 nulos, 4 catálogo, 5 sublenguaje completo, 8 y 9 independencia física y lógica, 11 distribución, 12 no subversión.
- Clave candidata = mínima. Superclave = no necesariamente mínima. Clave primaria = sin nulos y una por tabla. UNIQUE = puede admitir nulos.
- Integridad referencial: la clave foránea apunta a una fila que existe. ON DELETE RESTRICT impide el borrado; CASCADE borra las hijas; SET NULL las pone a nulo.
- Grado = columnas; cardinalidad = filas.
- CREATE, ALTER, DROP y TRUNCATE = DDL. SELECT, INSERT, UPDATE, DELETE y MERGE = DML. GRANT y REVOKE = DCL. COMMIT, ROLLBACK y SAVEPOINT = TCL.
- **TRUNCATE** vacía la tabla y la conserva. DROP la elimina con su definición. DELETE borra filas con WHERE y registra cada una.
- WHERE filtra filas antes de agrupar; HAVING filtra grupos. COUNT(*) cuenta filas; COUNT(col) ignora los nulos. NULL = NULL no es verdadero: se usa IS NULL.
- UNION elimina duplicados; UNION ALL los conserva. EXCEPT es la norma; MINUS es de Oracle. LIMIT y TOP no son de la norma (FETCH FIRST sí).
- LEFT JOIN conserva todas las filas de la izquierda.
- Vista = tabla virtual; la materializada guarda los datos. Índice = más velocidad de lectura, más coste de escritura y de espacio.
- ACID = atomicidad, consistencia, aislamiento y durabilidad. COMMIT y ROLLBACK → atomicidad.
- READ COMMITTED evita las lecturas sucias; REPEATABLE READ, además, las no repetibles; SERIALIZABLE, todas.
- 2PL: crecimiento y decrecimiento. El estricto mantiene los bloqueos exclusivos hasta el COMMIT.
- WAL: primero el registro y luego el dato. REDO para las confirmadas y UNDO para las no confirmadas.
- CAP solo afecta a los sistemas distribuidos y su «C» no es la de ACID. BASE = consistencia eventual de NoSQL.
- **Cassandra** es NoSQL de columna ancha, no relacional. MySQL, MariaDB, Oracle, SQL Server, PostgreSQL y Db2 son relacionales.
- La norma SQL es ISO/IEC 9075 (vigente SQL:2023). SQL2 = SQL-92. SQL3 = SQL:1999.
- ODBC: Microsoft, basado en SQL/CLI. JDBC: Java; driver tipo 1 = puente ODBC, tipo 4 = Java puro. ADO.NET: .NET, con DataSet desconectado.
- Consultas parametrizadas contra la inyección SQL.
