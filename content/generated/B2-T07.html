Apuntes de estudio

0. Cómo estudiar este tema

El enunciado describe una forma de construir y operar aplicaciones con tres piezas que encajan entre sí:

  1. Contenedores. Empaquetan una aplicación con todo lo que necesita para ejecutarse igual en cualquier entorno.
  2. Microservicios. Dividen la aplicación en servicios pequeños que se despliegan por separado. Cada uno va en su contenedor.
  3. Un orquestador, normalmente Kubernetes, que ejecuta cientos de contenedores en un clúster, los mantiene vivos, los conecta y los escala.

Después, el enunciado pide las tres tareas de operación: desplegar (CI/CD, estrategias de despliegue, GitOps), monitorizar (métricas, registros, trazas) y escalar (más réplicas, más recursos, más nodos).

Una idea atraviesa todo el tema: los contenedores y Kubernetes son tecnologías; los microservicios son una decisión de arquitectura con costes. Se pueden usar contenedores sin microservicios, y en un supuesto hay que justificar los microservicios, no darlos por supuestos.

Qué ha preguntado el INAP en este tema (3 preguntas):

  • Cuál es el mecanismo preferido de Docker para persistir datos: los volúmenes (2019).
  • Cuándo usar un registro de contenedores público: para pequeños proyectos de código abierto (2022).
  • Qué configuración permite a un contenedor ver los procesos del nodo: hostPID: true (2025).

Además, el INAP ha preguntado CI/CD, DevOps, Jenkins, Maven, Ansible, ELK y los tipos de hipervisor en preguntas que clasifica en B3-T06, B4-T04 y B4-T06. Se explican aquí en lo que son despliegue y monitorización, y se listan en el apartado 11.

Qué se estudia en otros temas:

  • Cliente-servidor, SOA, servicios web, REST y patrones de resiliencia: B2-T06.
  • Computación en la nube (IaaS, PaaS, SaaS): B2-T01.
  • Metodologías ágiles y DevOps en detalle: B3-T06.
  • Pruebas del software: B3-T07.
  • Migración de aplicaciones: B3-T08.
  • Gestión de la configuración, control de versiones, automatización de la operación y monitorización de sistemas: B4-T04.
  • Virtualización de servidores, alta disponibilidad y balanceo: B4-T06.

1. De la virtualización a los contenedores

1.1 Virtualización por hardware: máquinas virtuales

La virtualización hace que unos recursos físicos (procesador, memoria, red, almacenamiento) funcionen como varios recursos lógicos independientes. En la virtualización de servidores, un hipervisor reparte la máquina física (anfitrión) entre varias máquinas virtuales (invitados), cada una con su propio sistema operativo completo.

Hay dos tipos de hipervisor (preguntas 2022 · 81 y 2024 · 82, clasificadas en B4-T06):

TipoDónde se ejecutaEjemplos
Tipo 1, nativo o bare metalDirectamente sobre el hardware; ocupa el lugar del sistema operativo anfitriónVMware ESXi, Microsoft Hyper-V, Xen, KVM
Tipo 2, alojado (hosted)Como una aplicación sobre un sistema operativo convencionalOracle VirtualBox, VMware Workstation

KVM es un caso mixto: convierte el núcleo Linux en hipervisor de tipo 1, pero el sistema anfitrión sigue siendo un Linux completo.

Técnicas de virtualización del procesador:

  • Virtualización completa: el invitado se ejecuta sin modificar. Antiguamente se lograba con traducción binaria de las instrucciones privilegiadas, con bastante sobrecarga. Hoy se apoya en la asistencia por hardware de los procesadores (Intel VT-x, AMD-V), con un rendimiento cercano al nativo.
  • Paravirtualización: el núcleo del invitado se modifica para llamar directamente al hipervisor (hypercalls) en lugar de ejecutar instrucciones privilegiadas. Fue la técnica original de Xen. Hoy se usa sobre todo para los controladores de disco y red (virtio).
  • Emulación: se simula un procesador distinto, por ejemplo con QEMU. Es lenta, pero permite ejecutar software de otra arquitectura.

1.2 Virtualización del sistema operativo: contenedores

En la virtualización a nivel de sistema operativo no hay hipervisor ni sistemas invitados. Un único núcleo ejecuta varios entornos aislados, llamados contenedores. Cada contenedor ve su propio sistema de ficheros, procesos, red y usuarios, pero todos comparten el núcleo del anfitrión.

Consecuencias:

  • Todos los contenedores usan el mismo núcleo, aunque no la misma distribución. En un anfitrión Red Hat pueden ejecutarse contenedores con Ubuntu o Alpine.
  • Un contenedor Linux necesita un núcleo Linux. En Windows o macOS, Docker Desktop lo ejecuta dentro de una máquina virtual Linux ligera. Existen también contenedores Windows, que necesitan un núcleo Windows.
  • La imagen debe corresponder a la arquitectura del procesador (amd64, arm64) o publicarse para varias.

1.3 Contenedor frente a máquina virtual

AspectoContenedorMáquina virtual
Qué virtualizaEl sistema operativo (procesos aislados)El hardware
NúcleoCompartido con el anfitriónUno propio por máquina
TamañoMegabytesGigabytes

No son excluyentes: lo habitual es ejecutar contenedores dentro de máquinas virtuales, en el centro de datos propio o en la nube. Existen también entornos de ejecución que dan a cada contenedor una máquina virtual ligera (Kata Containers) o un núcleo simulado (gVisor), para cargas que necesitan más aislamiento.

1.4 Un poco de historia

  • 1979: chroot en Unix, que cambia el directorio raíz de un proceso.
  • 2000: jails de FreeBSD. 2004: zonas de Solaris. 2005: OpenVZ.
  • 2008: LXC (Linux Containers), con los mecanismos del núcleo Linux.
  • 2013: Docker populariza los contenedores con un formato de imagen y una herramienta sencilla.
  • 2014: Google publica Kubernetes, basado en su sistema interno Borg.
  • 2015: se crean la Open Container Initiative (OCI) y la Cloud Native Computing Foundation (CNCF), ambas en la Linux Foundation. Kubernetes 1.0 se cede a la CNCF.

2. Contenedores

2.1 Cómo aísla el núcleo Linux

Un contenedor es, para el sistema operativo, un proceso normal con restricciones. Los mecanismos son:

  • Espacios de nombres (namespaces): dan al proceso su propia visión de un recurso.
    • PID: sus propios números de proceso; desde dentro solo ve los procesos del contenedor.
    • Mount: su propio árbol de sistemas de ficheros.
    • Network: sus propias interfaces, direcciones y puertos.
    • IPC: su propia comunicación entre procesos.
    • UTS: su propio nombre de equipo.
    • User: sus propios usuarios; el root del contenedor puede ser un usuario sin privilegios en el anfitrión.
    • Cgroup y time.
  • Grupos de control (cgroups, hoy en su versión 2): limitan y contabilizan los recursos que consume el proceso: CPU, memoria, E/S, número de procesos.
  • Capabilities: dividen los privilegios de root en piezas que se pueden quitar una a una.
  • seccomp, AppArmor y SELinux: restringen las llamadas al sistema y los accesos.
  • Sistemas de ficheros por capas (OverlayFS).

Los espacios de nombres explican la pregunta 2025 · 31: si un Pod se configura con hostPID: true, comparte el espacio de nombres de procesos del nodo y puede ver todos sus procesos (apartado 10.3).

2.2 Imagen, capas y contenedor

  • Una imagen es una plantilla inmutable con el sistema de ficheros de la aplicación (binarios, bibliotecas, configuración) y sus metadatos (orden de arranque, variables, puertos). Se compone de capas superpuestas. Las capas se comparten entre imágenes, lo que ahorra espacio y tiempo de descarga.
  • Un contenedor es una instancia en ejecución de una imagen. Añade encima una capa escribible propia, que desaparece al borrar el contenedor.
  • Una imagen se identifica por su nombre y etiqueta (registro/proyecto/app:1.4.2) o, de forma inmutable, por su resumen criptográfico (digest, sha256:…). La etiqueta latest no significa «la última versión»: es solo la etiqueta por defecto y puede apuntar a cualquier cosa.

La relación es como la de una clase y sus objetos: de una imagen se arrancan muchos contenedores iguales.

2.3 Estándares OCI y entornos de ejecución

La Open Container Initiative (2015) define tres especificaciones para que las imágenes y los contenedores no dependan de un producto:

  1. Especificación de imagen (image-spec): formato de la imagen y sus capas.
  2. Especificación de ejecución (runtime-spec): cómo se crea y ejecuta un contenedor a partir de un paquete en disco.
  3. Especificación de distribución (distribution-spec): la API HTTP para subir y descargar imágenes de un registro.

Gracias a ellas, una imagen construida con Docker se ejecuta con Podman, containerd o CRI-O, y se guarda en cualquier registro compatible.

Entornos de ejecución (runtimes), de bajo a alto nivel:

  • runc: el entorno de bajo nivel de referencia de la OCI. Crea el proceso con sus espacios de nombres y cgroups.
  • containerd (CNCF) y CRI-O: entornos de alto nivel que descargan imágenes, gestionan su almacenamiento y llaman a runc. Kubernetes se comunica con ellos mediante la interfaz CRI (Container Runtime Interface).
  • Docker Engine se apoya en containerd y runc. Kubernetes dejó de usar Docker Engine directamente en la versión 1.24 (2022), al eliminar el adaptador dockershim. Las imágenes construidas con Docker siguen funcionando, porque son OCI.

2.4 Docker

Docker (2013) es la plataforma que popularizó los contenedores. Su arquitectura es cliente-servidor:

  • El cliente (docker) envía órdenes al demonio.
  • El demonio (dockerd) construye imágenes y gestiona contenedores, redes y volúmenes, apoyándose en containerd y runc.
  • Un registro guarda las imágenes. El público por defecto es Docker Hub.

Moby es el proyecto de código abierto del que se construye Docker, no una herramienta de gestión. Podman es una alternativa compatible sin demonio que puede ejecutar contenedores sin privilegios de root. Docker Desktop, la aplicación para puestos de trabajo, exige suscripción de pago en organizaciones grandes, lo que conviene tener en cuenta en la Administración.

El Dockerfile describe cómo construir una imagen, instrucción a instrucción:

InstrucciónFunción
FROMImagen base
RUNEjecuta una orden durante la construcción y crea una capa
COPY y ADDCopian ficheros a la imagen (ADD admite además URL y descomprime archivos)
WORKDIRDirectorio de trabajo
ENV y ARGVariables de entorno (en ejecución) y argumentos de construcción
EXPOSEDocumenta el puerto que escucha la aplicación; no lo publica
USERUsuario con el que se ejecuta el proceso
ENTRYPOINT y CMDPrograma que se ejecuta al arrancar y sus argumentos por defecto; CMD se sustituye fácilmente al arrancar
HEALTHCHECKOrden para comprobar si el contenedor está sano

Buenas prácticas de construcción:

  • Construcción en varias etapas (multi-stage): se compila en una imagen con todas las herramientas y se copia solo el resultado a una imagen final mínima.
  • Imágenes base mínimas (Alpine, distroless) y con versión fijada.
  • Ejecutar con un usuario sin privilegios, no como root.
  • No incluir secretos en la imagen: quedan en sus capas aunque se borren después.
  • Un proceso principal por contenedor.
  • Un fichero .dockerignore para no copiar lo que no hace falta.
  • Construir una vez y desplegar muchas (build once, deploy many): la misma imagen pasa por todos los entornos, y solo cambia la configuración.

Docker Compose describe en un fichero YAML (compose.yaml) una aplicación de varios contenedores, con sus redes y volúmenes, y la arranca con una sola orden. Es útil en desarrollo y en despliegues sencillos de un solo servidor. Para un clúster se usa un orquestador.

2.5 Almacenamiento: los volúmenes

La capa escribible de un contenedor se pierde al borrarlo y es lenta. Para que los datos sobrevivan, Docker ofrece tres mecanismos:

MecanismoQué esUso
VolumenAlmacenamiento que gestiona Docker, fuera del ciclo de vida del contenedorEl mecanismo preferido para persistir datos: bases de datos, ficheros subidos
Montaje enlazado (bind mount)Un directorio concreto del anfitrión montado en el contenedorDesarrollo (código fuente) o ficheros de configuración del anfitrión
tmpfsMemoria del anfitrión, que no se escribe en discoDatos temporales o sensibles que no deben persistir

La pregunta 2019 · 27 pedía el mecanismo preferido de Docker para persistir datos: los volúmenes. Los distractores (bases de datos estructuradas, NoSQL, colas de mensajes) son lugares donde una aplicación guarda datos, no mecanismos de Docker. Los volúmenes son preferibles a los montajes enlazados porque no dependen de la estructura de directorios del anfitrión, se gestionan con las órdenes de Docker, se pueden compartir entre contenedores y admiten controladores para almacenamiento remoto.

2.6 Registros de imágenes

Un registro (registry) almacena y distribuye imágenes, organizadas en repositorios y etiquetas.

  • Públicos: cualquiera puede descargar las imágenes. Docker Hub, Quay.io, GitHub Container Registry. Son adecuados para distribuir software de código abierto, sobre todo en proyectos pequeños que no quieren mantener infraestructura propia (pregunta 2022 · 23).
  • Privados: con control de acceso, para las imágenes propias de la organización, cuando la seguridad o la confidencialidad son prioritarias. Pueden ser gestionados por un proveedor de nube (Amazon ECR, Azure Container Registry, Google Artifact Registry) o instalados en el centro propio (Harbor, de la CNCF; Nexus; Artifactory; GitLab).

Los distractores de la 2022 · 23 asociaban el registro público a mantenerlo en las propias instalaciones o a la seguridad, que son motivos para uno privado, o decían que no deben usarse nunca.

Un registro privado suele incluir análisis de vulnerabilidades, firma de imágenes, réplica entre centros y políticas de retención. Conviene también tener un espejo interno de las imágenes públicas que se usan, para no depender de su disponibilidad ni de sus límites de descarga.

3. Microservicios

3.1 Definición y características

Una arquitectura de microservicios construye una aplicación como un conjunto de servicios pequeños, cada uno con su propio proceso, que se comunican por mecanismos ligeros (HTTP, mensajería) y se despliegan de forma independiente. Cada servicio corresponde a una capacidad de negocio y es responsable de sus datos.

James Lewis y Martin Fowler (2014) describieron sus características comunes:

  1. Componentes como servicios: la unidad de modularidad es un servicio que se despliega por separado, no una biblioteca.
  2. Organización en torno a capacidades de negocio, con equipos multidisciplinares, no por capas técnicas.
  3. Productos, no proyectos: el equipo que construye un servicio lo opera durante toda su vida («lo construyes, lo ejecutas»).
  4. Extremos inteligentes y tuberías tontas: la lógica está en los servicios; la comunicación es simple, sin un bus que la concentre (frente al ESB de SOA, B2-T06).
  5. Gobierno descentralizado: cada equipo elige la tecnología más adecuada.
  6. Gestión descentralizada de datos: cada servicio tiene su base de datos.
  7. Automatización de la infraestructura: pruebas, integración y despliegue automáticos.
  8. Diseño para el fallo: cualquier servicio puede fallar y los demás deben tolerarlo.
  9. Diseño evolutivo: los servicios se sustituyen o reescriben con facilidad.

Ley de Conway (1968): la estructura de un sistema tiende a reproducir la estructura de comunicación de la organización que lo diseña. Por eso los microservicios van de la mano de equipos autónomos por producto.

Diseño guiado por el dominio (DDD, Eric Evans, 2003): la frontera de un microservicio suele coincidir con un contexto delimitado (bounded context), una parte del negocio con su propio modelo y vocabulario.

3.2 Monolito, monolito modular, SOA y microservicios

  • Monolito: la aplicación se construye y despliega como una sola unidad, aunque esté bien organizada en capas. Es sencillo de desarrollar, probar y operar al principio. Cualquier cambio obliga a desplegarlo entero, y se escala replicando todo.
  • Monolito modular: un monolito dividido en módulos con fronteras y contratos internos claros. Es a menudo la mejor opción para un equipo pequeño o un dominio todavía cambiante, y facilita extraer microservicios más adelante.
  • Microservicios: servicios pequeños desplegables por separado.
  • SOA: busca integrar y reutilizar servicios en toda la organización, a menudo con un ESB y datos compartidos. Los microservicios buscan la independencia de despliegue, con datos propios y comunicación ligera.

3.3 Ventajas, inconvenientes y cuándo usarlos

Ventajas:

  • Despliegue independiente y frecuente de cada servicio.
  • Escalado selectivo de los servicios con más carga.
  • Aislamiento de fallos (con los patrones de resiliencia adecuados).
  • Autonomía de los equipos y libertad tecnológica.
  • Servicios pequeños, más fáciles de entender y de sustituir.

Inconvenientes:

  • Complejidad de sistema distribuido: red, latencia, fallos parciales (las falacias de B2-T06).
  • Consistencia de datos entre servicios sin transacciones distribuidas.
  • Operación: muchos artefactos que construir, desplegar, monitorizar y proteger; exige automatización y una plataforma madura.
  • Pruebas y depuración de interacciones entre servicios.
  • Seguridad «este-oeste» (entre servicios) además de la perimetral.
  • Riesgo de monolito distribuido: servicios tan acoplados que hay que desplegarlos juntos, con todos los inconvenientes de ambos mundos. Suele aparecer al dividir por tablas o capas técnicas en lugar de por dominio, o al compartir la base de datos.

Se justifican cuando hay fronteras de dominio claras, varios equipos que necesitan desplegar sin coordinarse, partes con necesidades de escalado muy distintas y una organización capaz de automatizar y operar la plataforma. No se justifican en una aplicación pequeña, con un solo equipo o con un dominio aún sin estabilizar.

3.4 La aplicación de doce factores

La metodología 12-factor app (Adam Wiggins, Heroku, 2011) resume cómo construir aplicaciones que se despliegan bien en contenedores y nube:

  1. Código base: un repositorio por aplicación, con muchos despliegues.
  2. Dependencias: declaradas explícitamente y aisladas.
  3. Configuración: en el entorno (variables), no en el código.
  4. Servicios de respaldo (bases de datos, colas): recursos conectables por URL.
  5. Construir, publicar, ejecutar: etapas separadas.
  6. Procesos sin estado: el estado va a servicios de respaldo.
  7. Asignación de puertos: la aplicación expone su servicio por un puerto.
  8. Concurrencia: se escala añadiendo procesos.
  9. Desechabilidad: arranque rápido y parada ordenada.
  10. Paridad entre desarrollo y producción.
  11. Registros como flujos de eventos por la salida estándar.
  12. Procesos de administración como tareas puntuales.

3.5 Datos y consistencia

  • Una base de datos por servicio. Compartir una base de datos entre servicios acopla sus esquemas y sus despliegues. Cada servicio expone sus datos solo por su API o por eventos.
  • Saga. Una transacción de negocio que afecta a varios servicios se divide en transacciones locales. Si una falla, se ejecutan transacciones compensatorias que deshacen las anteriores. Puede coordinarse por orquestación (un coordinador) o por coreografía (eventos).
  • Bandeja de salida (transactional outbox): el evento se guarda en la base de datos del servicio en la misma transacción que el cambio, y otro proceso lo publica. Evita publicar eventos de cambios no confirmados.
  • CQRS: separar el modelo de escritura del de lectura, cuando las consultas son muy distintas de las actualizaciones.
  • Abastecimiento de eventos (event sourcing): guardar la secuencia de eventos en lugar del estado actual.

La consistencia eventual obliga a diseñar estados intermedios («solicitud en trámite») y a explicarlos al usuario.

3.6 Patrones de comunicación e infraestructura

  • Pasarela de API (API gateway): punto de entrada único que encamina las peticiones a los servicios y centraliza autenticación, límites de uso y registro (B2-T06).
  • Backend for frontend (BFF): una pasarela específica para cada tipo de cliente.
  • Descubrimiento de servicios: los servicios se localizan por nombre, no por dirección fija, porque sus instancias cambian. En Kubernetes lo resuelven los Service y el DNS del clúster.
  • Comunicación síncrona (REST, gRPC) o asíncrona (eventos y colas), según el acoplamiento que se admita.
  • Resiliencia: tiempos de espera, reintentos, cortacircuitos y compartimentos estancos (B2-T06).
  • Sidecar: un contenedor auxiliar junto al principal, en el mismo Pod, que añade una función transversal (proxy, recogida de registros) sin tocar la aplicación. Kubernetes tiene contenedores sidecar nativos, estables desde la versión 1.33 (2025).
  • Malla de servicios (service mesh): una capa de infraestructura que gestiona la comunicación entre servicios. Cifra con TLS mutuo, aplica reintentos y tiempos de espera, reparte el tráfico por porcentajes y genera métricas y trazas, sin cambiar el código. Ejemplos: Istio y Linkerd, ambos de la CNCF. Clásicamente usa un proxy (Envoy) como sidecar en cada Pod; Istio ofrece también un modo sin sidecars (ambient).
  • Estrangulador (strangler fig): para migrar un monolito, se colocan delante una pasarela y se van extrayendo funciones a servicios nuevos, hasta que el monolito desaparece.

4. Kubernetes: arquitectura

Kubernetes: control plane, nodos y objetos

4.1 Qué es un orquestador

Ejecutar unos pocos contenedores a mano es fácil. Ejecutar cientos en decenas de servidores exige un orquestador que:

  • Decida en qué servidor se ejecuta cada contenedor (planificación).
  • Reinicie o sustituya los que fallan (autorreparación).
  • Les dé direcciones estables y reparta el tráfico (descubrimiento y balanceo).
  • Despliegue versiones nuevas sin cortar el servicio y permita volver atrás.
  • Ajuste el número de réplicas a la carga (escalado).
  • Gestione configuración, secretos y almacenamiento.

Kubernetes (abreviado K8s) es el orquestador de referencia. Lo publicó Google en 2014, basado en su sistema interno Borg; la versión 1.0 (2015) se cedió a la CNCF, de la que fue el primer proyecto graduado (2018). Alternativas: Docker Swarm, HashiCorp Nomad y Amazon ECS.

Kubernetes publica tres versiones menores al año y mantiene las tres últimas, cada una con unos catorce meses de soporte. En noviembre de 2026 la última es la 1.37 (agosto de 2026), y la 1.38 está prevista para diciembre. Para el examen importan los conceptos, no los números de versión.

4.2 Modelo declarativo y reconciliación

Kubernetes es declarativo: el usuario no da órdenes («arranca tres contenedores»), sino que describe el estado deseado en un manifiesto YAML («quiero tres réplicas de esta imagen»). Los controladores comparan continuamente el estado deseado con el real y actúan para igualarlos. Es el bucle de reconciliación.

Si un nodo cae y se pierde una réplica, nadie tiene que intervenir: el controlador detecta que hay dos en vez de tres y crea otra en un nodo sano.

4.3 Plano de control

El plano de control (control plane) toma las decisiones del clúster. En producción se replica en tres o más nodos para alta disponibilidad.

  • kube-apiserver: la API del clúster y su único punto de entrada. Todos los componentes y usuarios (por ejemplo, con kubectl) hablan con él. Autentica, autoriza, valida y guarda los objetos.
  • etcd: almacén clave-valor distribuido y consistente donde se guarda todo el estado del clúster. Usa el algoritmo de consenso Raft. Es lo primero que hay que respaldar.
  • kube-scheduler: asigna cada Pod nuevo a un nodo según los recursos que pide y las restricciones (afinidades, taints).
  • kube-controller-manager: ejecuta los controladores (de réplicas, de nodos, de endpoints, de cuentas de servicio…).
  • cloud-controller-manager: integra el clúster con el proveedor de nube (balanceadores, discos, nodos).

4.4 Nodos

Los nodos de trabajo ejecutan las cargas:

  • kubelet: agente de cada nodo. Recibe del API los Pods asignados, pide al entorno de ejecución que los arranque, comprueba sus sondas de salud e informa de su estado.
  • Entorno de ejecución de contenedores: containerd o CRI-O, a través de la interfaz CRI.
  • kube-proxy: programa las reglas de red que hacen funcionar los Service. Algunos complementos de red, como Cilium, lo sustituyen.

4.5 Complementos e interfaces

Kubernetes delega en complementos mediante interfaces estándar:

  • CRI (Container Runtime Interface): entorno de ejecución.
  • CNI (Container Network Interface): red entre Pods (Calico, Cilium, Flannel). Todos los Pods del clúster se ven entre sí con su propia IP, sin NAT.
  • CSI (Container Storage Interface): almacenamiento persistente de cualquier fabricante.
  • DNS del clúster (CoreDNS): resuelve los nombres de los Service.

5. Objetos de Kubernetes

5.1 Pod

El Pod es la unidad mínima de despliegue de Kubernetes, no el contenedor. Es un grupo de uno o varios contenedores que:

  • Se planifican juntos en el mismo nodo.
  • Comparten la red (una IP; se hablan por localhost) y pueden compartir volúmenes.
  • Nacen y mueren juntos.

Lo normal es un contenedor principal por Pod, a veces con sidecars o contenedores de inicio (init containers) que preparan el entorno antes de arrancar. Los Pods son efímeros: no se reparan, se sustituyen por otros con otra IP. Por eso casi nunca se crean directamente, sino a través de un controlador.

5.2 Controladores de cargas de trabajo

ObjetoFunciónUso típico
ReplicaSetMantiene un número de réplicas idénticas de un PodCasi nunca se usa directamente
DeploymentGestiona ReplicaSets para hacer actualizaciones progresivas y vueltas atrás de forma declarativaAplicaciones sin estado: web, API
StatefulSetPods con identidad estable (nombre y orden fijos) y almacenamiento propio que se conservaBases de datos, colas, sistemas en clúster
DaemonSetUna copia en cada nodo (o en los seleccionados)Agentes de registros, monitorización o red
JobEjecuta Pods hasta completar una tareaProcesos por lotes, migraciones
CronJobCrea Jobs periódicamenteTareas programadas, copias

Relación clave: el Deployment crea un ReplicaSet, y el ReplicaSet crea los Pods. Al cambiar la imagen, el Deployment crea un ReplicaSet nuevo y traslada las réplicas poco a poco.

5.3 Red: Service, Ingress y Gateway API

Como los Pods cambian de IP, un Service da un nombre DNS y una IP estables a un conjunto de Pods, seleccionados por sus etiquetas, y reparte el tráfico entre ellos. Un Service de Kubernetes no es un microservicio de negocio: es un objeto de red.

Tipo de ServiceQué hace
ClusterIP (por defecto)IP interna, accesible solo desde el clúster
NodePortAdemás, abre el mismo puerto (30000–32767) en todos los nodos
LoadBalancerAdemás, crea un balanceador externo del proveedor de nube
ExternalNameAlias DNS hacia un nombre externo
Headless (sin IP de clúster)Devuelve directamente las IP de los Pods; lo usan los StatefulSet

Para el tráfico HTTP desde fuera del clúster:

  • Ingress: reglas de encaminamiento HTTP por nombre de dominio y ruta, con terminación TLS. Necesita un controlador que las aplique. La API sigue disponible, pero está congelada.
  • Gateway API (estable desde 2023): su sucesora, más expresiva y con funciones separadas por rol: el proveedor define la clase de gateway, los operadores de plataforma definen los Gateway y los equipos de aplicación definen las rutas (HTTPRoute, GRPCRoute). Permite, por ejemplo, repartir tráfico por pesos para un despliegue canario.
  • El controlador más usado, Ingress NGINX, se retiró en marzo de 2026: ya no recibe correcciones ni parches de seguridad. Kubernetes recomienda migrar a Gateway API u otro controlador.

NetworkPolicy restringe qué Pods pueden comunicarse entre sí (apartado 10.4).

5.4 Configuración y secretos

  • ConfigMap: configuración no sensible (parámetros, ficheros), que se inyecta en el Pod como variables de entorno o ficheros. Así la misma imagen sirve en todos los entornos.
  • Secret: datos sensibles (contraseñas, claves, certificados). Por defecto solo están codificados en Base64, no cifrados. Hay que activar el cifrado en reposo de etcd, limitar quién puede leerlos con RBAC y, en entornos exigentes, usar un gestor externo de secretos (HashiCorp Vault, los almacenes de claves de los proveedores de nube) con sus controladores.

5.5 Almacenamiento persistente

  • Volumen: directorio accesible por los contenedores del Pod. Algunos tipos son efímeros (emptyDir); otros, persistentes.
  • PersistentVolume (PV): un recurso de almacenamiento del clúster (un disco de la nube, un volumen de una cabina, un recurso NFS).
  • PersistentVolumeClaim (PVC): la solicitud de almacenamiento de una aplicación («10 GB, lectura y escritura por un nodo»). Kubernetes la asocia a un PV.
  • StorageClass: describe un tipo de almacenamiento y permite crear los PV dinámicamente cuando se pide un PVC.

Así la aplicación pide almacenamiento sin conocer la infraestructura, igual que pide CPU.

5.6 Organización

  • Namespace: partición lógica del clúster, con su propio ámbito de nombres, permisos, cuotas y políticas. Típicamente uno por equipo, aplicación o entorno.
  • Etiquetas (labels) y selectores: pares clave-valor que agrupan objetos. Los Service, Deployment y NetworkPolicy eligen sus Pods por etiquetas.
  • ResourceQuota y LimitRange: limitan los recursos totales de un namespace y fijan valores por defecto.
  • ServiceAccount: identidad de los Pods ante la API.

5.7 Recursos, calidad de servicio, salud y planificación

Peticiones y límites:

  • La petición (request) es la cantidad de CPU y memoria que el contenedor necesita. El planificador solo lo coloca en un nodo con esa capacidad libre.
  • El límite (limit) es el máximo que puede consumir. Si supera el límite de CPU, se le frena (throttling); si supera el de memoria, el núcleo lo mata (OOMKilled).

Según cómo se fijen, el Pod recibe una clase de calidad de servicio, que decide qué Pods se expulsan primero cuando el nodo se queda sin memoria:

  • Guaranteed: peticiones iguales a los límites en todos los contenedores. Se expulsa el último.
  • Burstable: tiene peticiones, pero menores que los límites.
  • BestEffort: sin peticiones ni límites. Se expulsa el primero.

Sondas de salud (probes), que ejecuta el kubelet:

SondaPreguntaSi falla
De arranque (startup)¿Ha terminado de arrancar?Las otras sondas esperan; si nunca arranca, se reinicia
De disponibilidad (readiness)¿Puede recibir tráfico ahora?Se saca del Service, pero no se reinicia
De vida (liveness)¿Sigue funcionando o se ha bloqueado?Se reinicia el contenedor

Una sonda de vida mal diseñada, por ejemplo que compruebe la base de datos, puede reiniciar todos los Pods a la vez cuando la base de datos va lenta y empeorar el incidente.

Planificación: además de los recursos, el planificador tiene en cuenta los selectores de nodo, las afinidades y antiafinidades (juntar o separar Pods, por ejemplo réplicas en zonas distintas), las taints y tolerancias (nodos que solo aceptan ciertos Pods) y la distribución por zonas. Un PodDisruptionBudget fija cuántas réplicas pueden faltar a la vez durante un mantenimiento.

6. Soluciones y ecosistema

6.1 Empaquetado y automatización

  • Helm: el «gestor de paquetes» de Kubernetes. Un chart es un conjunto de plantillas de manifiestos con valores parametrizables, que se instala, actualiza y revierte como una unidad (release).
  • Kustomize: personaliza manifiestos por entorno superponiendo cambios, sin plantillas. Está integrado en kubectl.
  • Operadores: amplían Kubernetes con recursos personalizados (CRD) y un controlador que sabe operar una aplicación concreta (crear una base de datos replicada, hacer copias, actualizarla). Automatizan el conocimiento de un administrador.

6.2 Distribuciones y servicios gestionados

ModalidadEjemplosCuándo
Kubernetes gestionado en la nubeAmazon EKS, Azure AKS, Google GKEEl proveedor opera el plano de control
Distribuciones empresarialesRed Hat OpenShift, SUSE Rancher, VMware TanzuCentro de datos propio o nube híbrida, con soporte y herramientas añadidas
Distribuciones ligerask3s, MicroK8s, kindEntornos pequeños, en el borde o de desarrollo
Contenedores como servicioAWS Fargate, Azure Container Apps, Google Cloud RunEjecutar contenedores sin gestionar clúster ni nodos

La CNCF certifica la conformidad de las distribuciones, que garantiza que las aplicaciones son portables entre ellas.

OpenShift, muy presente en la Administración, añade a Kubernetes construcción de imágenes, registro, consola, seguridad más estricta por defecto y soporte comercial.

6.3 Serverless

El modelo serverless o funciones como servicio (FaaS) lleva la abstracción un paso más allá: se despliegan funciones que se ejecutan en respuesta a eventos, y el proveedor gestiona todo, escala de cero a lo necesario y cobra por ejecución. Ejemplos: AWS Lambda, Azure Functions, Google Cloud Run functions y, sobre Kubernetes, Knative u OpenFaaS.

  • Ventajas: nada que administrar, escalado automático hasta cero, pago por uso.
  • Inconvenientes: arranque en frío, límites de duración y recursos, dependencia del proveedor y dificultad para depurar.

7. Despliegue

7.1 DevOps y SRE

DevOps es un conjunto de prácticas y una cultura que unen el desarrollo (Dev) y la operación (Ops) para entregar cambios con más frecuencia y fiabilidad. Se apoya en la automatización (CI/CD, infraestructura como código), la medición y la responsabilidad compartida. DevSecOps integra la seguridad en todo el ciclo, desde el diseño («desplazar a la izquierda»). Se estudian en B3-T06.

SRE (Site Reliability Engineering), creada en Google por Ben Treynor en 2003, consiste en aplicar la ingeniería de software a la operación. Ingenieros dedicados fijan objetivos de nivel de servicio (SLO), gestionan un presupuesto de error y automatizan el trabajo manual repetitivo. Google la describe como una forma concreta de aplicar DevOps.

7.2 Integración, entrega y despliegue continuos

CI/CD significa Continuous Integration / Continuous Delivery (pregunta 2022 · 22, clasificada en B3-T06). La segunda «D» puede ser también Continuous Deployment. Son tres niveles de madurez:

PrácticaQué se automatizaPaso a producción
Integración continua (CI)Cada cambio se integra en la rama común varias veces al día y se compila, prueba y analiza automáticamenteNo despliega
Entrega continua (CD)Además, se genera el artefacto y se despliega automáticamente en entornos de prueba y preproducción; el software está siempre listo para producciónCon una aprobación manual
Despliegue continuo (CD)Además, todo cambio que supera las pruebas llega a producciónAutomático, sin intervención

La integración continua no consiste en desplegar en producción automáticamente; ese era el distractor de la 2019 · 52.

Un pipeline típico para contenedores:

  1. El desarrollador sube un cambio al control de versiones (Git) y abre una petición de integración.
  2. El servidor de CI compila y ejecuta las pruebas unitarias.
  3. Análisis estático de calidad y seguridad del código (SonarQube, que analiza el código y lee los informes de cobertura, pero no ejecuta las pruebas). Un umbral de calidad (quality gate) detiene el pipeline si no se cumple.
  4. Construcción de la imagen, análisis de sus vulnerabilidades, generación de la SBOM y firma.
  5. Publicación en el registro.
  6. Despliegue en el entorno de pruebas y pruebas de integración y extremo a extremo.
  7. Promoción de la misma imagen a preproducción y producción.

Herramientas:

  • Servidores de CI/CD: Jenkins (servidor de automatización de código abierto escrito en Java, pregunta 2024 · 55, clasificada en B3-T06; sus pipelines se definen en un Jenkinsfile con un lenguaje basado en Groovy), GitLab CI/CD, GitHub Actions, Azure Pipelines (antes Team Foundation Server), Tekton.
  • Construcción: Maven (basado en el modelo de objetos de proyecto, POM, en un fichero pom.xml, pregunta 2024 · 56, clasificada en B3-T06), Gradle, npm, MSBuild.
  • Repositorios de artefactos: Nexus, Artifactory, Harbor.

7.3 Entornos

Los cambios pasan por varios entornos antes de producción: desarrollo (pruebas unitarias), integración, pruebas o calidad (pruebas extremo a extremo), preproducción (staging, lo más parecido posible a producción, para la aceptación de los usuarios) y producción.

Con contenedores, la diferencia entre entornos se reduce a la configuración (ConfigMap, Secret, valores de Helm). La imagen es la misma, lo que elimina el clásico «en mi máquina funciona». Kubernetes permite además crear entornos efímeros por cada petición de integración y destruirlos al cerrarla.

7.4 Infraestructura como código

La infraestructura como código (IaC) define servidores, redes, clústeres y su configuración en ficheros descriptivos versionados, que se gestionan igual que el código: revisión, historial, pruebas, vuelta atrás (pregunta 2019 · 52, clasificada en B3-T06).

  • Aprovisionamiento (crear la infraestructura): Terraform y su bifurcación libre OpenTofu, AWS CloudFormation, Pulumi.
  • Gestión de la configuración (configurar lo creado): Ansible, cuyas tareas y estado deseado se describen en ficheros YAML llamados playbooks (pregunta 2025 · 80, clasificada en B4-T04), Puppet y Chef.

La IaC permite infraestructura inmutable: en lugar de modificar un servidor en producción, se crea uno nuevo con la configuración actualizada y se retira el antiguo. Es lo que hacen los contenedores con las aplicaciones.

La misma idea se aplica a la documentación: documentación como código, versionada junto al código, revisada en las peticiones de integración y generada en el pipeline (pregunta 2025 · 57, clasificada en B3-T06).

7.5 Estrategias de despliegue

EstrategiaCómo funcionaVentajasInconvenientes
Recreación (recreate)Se paran todas las réplicas antiguas y se arrancan las nuevasSencilla; nunca conviven dos versionesCorte de servicio
Actualización progresiva (rolling update)Se sustituyen las réplicas poco a pocoSin corte; es la opción por defecto del DeploymentConviven dos versiones durante el despliegue; vuelta atrás lenta
Azul-verde (blue/green)Se despliega la versión nueva completa en paralelo y se conmuta todo el tráfico de golpeVuelta atrás instantánea; pruebas antes de conmutarDoble capacidad durante el cambio
Canario (canary)La versión nueva recibe primero un pequeño porcentaje del tráfico, que aumenta si las métricas son buenasRiesgo mínimo; validación con usuarios realesRequiere buena monitorización y reparto de tráfico
Pruebas A/BDos versiones a grupos distintos de usuarios para comparar resultados de negocioDecisiones basadas en datosEs experimentación, no solo despliegue
Lanzamiento oscuro o en sombra (shadow)La versión nueva recibe una copia del tráfico real, pero sus respuestas se descartanPrueba con carga real sin afectar a nadieCuidado con los efectos secundarios (escrituras, correos)

En el Deployment, la actualización progresiva se regula con dos parámetros: maxSurge (cuántas réplicas de más puede haber durante el cambio) y maxUnavailable (cuántas pueden faltar). Ambos valen el 25 % por defecto. Si algo falla, kubectl rollout undo vuelve a la versión anterior.

Las banderas de funcionalidad (feature flags) separan el despliegue del código de la activación de la funcionalidad: el código llega a producción desactivado y se enciende para quien se quiera.

En cualquier estrategia, los cambios de esquema de base de datos deben ser compatibles hacia atrás, porque durante un tiempo conviven las dos versiones de la aplicación.

7.6 GitOps

GitOps (término de Weaveworks, 2017) aplica la idea de la IaC a los despliegues. Sus cuatro principios (OpenGitOps):

  1. Declarativo: el estado deseado del sistema está descrito de forma declarativa.
  2. Versionado e inmutable: ese estado se guarda en un repositorio Git, con todo su historial.
  3. Extraído automáticamente: un agente dentro del clúster extrae (pull) los cambios del repositorio. El pipeline no necesita credenciales del clúster.
  4. Reconciliado continuamente: el agente compara el clúster con el repositorio y corrige cualquier desviación, incluidas las manuales.

Desplegar consiste en aprobar un cambio en el repositorio, y volver atrás, en revertirlo. Herramientas: Argo CD y Flux, ambas de la CNCF. Para despliegues canarios automáticos, Argo Rollouts y Flagger.

8. Monitorización y observabilidad

8.1 Monitorización frente a observabilidad

  • Monitorización: vigilar indicadores conocidos y avisar cuando se salen de lo normal. Responde «¿funciona?».
  • Observabilidad: poder deducir por qué se comporta así el sistema a partir de sus señales, incluso ante fallos nuevos. Responde «¿qué le pasa?».

En microservicios hace falta observabilidad: una petición atraviesa muchos servicios, y un fallo en uno se manifiesta en otro.

8.2 Las tres señales

SeñalQué esHerramientas
MétricasValores numéricos en el tiempo: peticiones por segundo, latencia, uso de CPUPrometheus (recoge las métricas por consulta periódica, pull, y las consulta con PromQL), Alertmanager, Grafana para los paneles
Registros (logs)Sucesos con texto y contextoPilas ELK (Elasticsearch, Logstash y Kibana: búsqueda, análisis y visualización, pregunta 2024 · 79, clasificada en B4-T04) y EFK (con Fluentd o Fluent Bit); Grafana Loki
Trazas distribuidasEl recorrido de una petición por todos los servicios, con el tiempo de cada tramoJaeger, Zipkin, Grafana Tempo

OpenTelemetry (CNCF, 2019) es el estándar abierto para generar y enviar las tres señales con independencia de la herramienta que las almacene. Las trazas se correlacionan con un identificador que viaja en la cabecera W3C Trace Context.

En contenedores, la aplicación escribe los registros en la salida estándar (factor 11) y un agente en cada nodo (DaemonSet) los recoge y envía. No se escriben en ficheros dentro del contenedor, que desaparecen con él.

En Kubernetes, además: metrics-server (uso de CPU y memoria, que usa el HPA), kube-state-metrics (estado de los objetos) y los eventos del clúster.

8.3 Qué medir

  • Las cuatro señales doradas (libro de SRE de Google, 2016): latencia, tráfico, errores y saturación.
  • Método RED, para servicios: tasa de peticiones (rate), errores y duración (duration).
  • Método USE, para recursos (Brendan Gregg): utilización, saturación y errores.

Objetivos de servicio:

  • SLI (indicador): lo que se mide. Por ejemplo, el porcentaje de peticiones respondidas en menos de 300 ms.
  • SLO (objetivo): el valor que se quiere alcanzar. Por ejemplo, el 99,9 % al mes.
  • SLA (acuerdo): el compromiso con el cliente, con consecuencias si se incumple. Debe ser menos exigente que el SLO.
  • Presupuesto de error: lo que permite el SLO. Un 99,9 % mensual deja unos 43 minutos de indisponibilidad al mes. Si se agota, se frenan los despliegues y se prioriza la estabilidad.

Las alertas deben avisar de lo que afecta al usuario (incumplir o estar a punto de incumplir un SLO), no de cada métrica anómala, para evitar el ruido.

9.2 El HPA

El HPA ajusta periódicamente el número de réplicas de un Deployment o StatefulSet para mantener una métrica en un valor objetivo: normalmente el uso medio de CPU respecto a lo pedido, pero también memoria o métricas propias (peticiones por segundo, longitud de una cola). Su fórmula es:

réplicas deseadas = ⌈ réplicas actuales × valor actual de la métrica ÷ valor objetivo ⌉

Ejemplo: 4 réplicas con un uso medio de CPU del 90 % y un objetivo del 60 % dan ⌈4 × 90 ÷ 60⌉ = 6 réplicas. Se fijan un mínimo y un máximo, y una ventana de estabilización para no oscilar.

Requisitos y límites:

  • Los Pods deben tener peticiones de recursos (el porcentaje se calcula sobre ellas) y el clúster, metrics-server.
  • La aplicación debe ser sin estado o tener el estado fuera (base de datos, caché compartida) para que cualquier réplica pueda atender cualquier petición.
  • Añadir Pods no sirve si no hay nodos libres: el HPA se combina con el escalado del clúster.
  • Escalar una capa no elimina los cuellos de botella de otra: si la base de datos, una cola o un servicio externo están saturados, más réplicas pueden empeorarlo.
  • No conviene que el HPA y el VPA actúen sobre la misma métrica de CPU o memoria.

10. Seguridad de contenedores

10.1 Las cuatro capas

Kubernetes describe la seguridad en cuatro capas concéntricas, las «4C»: nube o centro de datos, clúster, contenedor y código. Cada capa depende de la exterior.

10.2 Cadena de suministro

  • Imágenes base de confianza y mínimas, actualizadas.
  • Análisis de vulnerabilidades de las imágenes en el pipeline y en el registro (Trivy, Grype, Clair).
  • SBOM (lista de componentes del software) en formato SPDX (ISO/IEC 5962:2021) o CycloneDX (ECMA-424). El Reglamento europeo de ciberresiliencia (2024/2847) la exige para los productos con elementos digitales.
  • Firma de imágenes y verificación antes de desplegar (Sigstore y cosign).
  • Procedencia verificable de la construcción, con los niveles del marco SLSA.
  • Políticas de admisión que impidan desplegar imágenes no firmadas, de registros no autorizados o con vulnerabilidades críticas (Kyverno, OPA Gatekeeper).

10.3 Seguridad de los Pods

El contexto de seguridad (securityContext) del Pod y de cada contenedor fija sus privilegios. Las opciones peligrosas rompen el aislamiento de los espacios de nombres o dan privilegios del nodo:

OpciónEfecto
hostPID: trueEl Pod comparte el espacio de nombres de procesos del nodo: puede ver (con ps o en /proc) todos los procesos del anfitrión y de otros contenedores, sus argumentos y variables, y, con privilegios, actuar sobre ellos
hostNetwork: trueUsa la red del nodo: puede escuchar en sus puertos y ver su tráfico
hostIPC: trueComparte la comunicación entre procesos del nodo
privileged: trueConcede todas las capabilities y acceso a los dispositivos del nodo. Es casi tener root en el anfitrión, pero por sí solo no comparte el espacio de nombres de procesos
allowPrivilegeEscalation: truePermite que un proceso gane más privilegios que su padre (por ejemplo, con programas setuid)
Volumen hostPathMonta un directorio del nodo; da acceso a esos ficheros, no a los procesos (salvo que se monte /proc del nodo)
runAsUser: 0 o sin runAsNonRootEl proceso se ejecuta como root dentro del contenedor

Por eso, en la pregunta 2025 · 31, un contenedor que lista los procesos del nodo apunta a hostPID: true. Los distractores dan privilegios o acceso a ficheros, pero no la visibilidad de los procesos.

Los estándares de seguridad de Pods (Pod Security Standards) definen tres niveles, que el controlador de admisión Pod Security aplica por namespace en modo de bloqueo, auditoría o aviso:

  • Privileged: sin restricciones; solo para componentes del sistema.
  • Baseline: impide las escaladas conocidas: compartir los espacios de nombres del nodo (hostPID, hostIPC, hostNetwork), contenedores privilegiados, volúmenes hostPath y capabilities peligrosas.
  • Restricted: además, obliga a ejecutar sin root, prohíbe la escalada de privilegios, elimina todas las capabilities y exige un perfil seccomp.

Sustituyeron a las PodSecurityPolicy, eliminadas en la versión 1.25 (2022).

10.4 Seguridad del clúster

  • RBAC: permisos por roles (Role y ClusterRole) asignados a usuarios, grupos y ServiceAccounts (RoleBinding y ClusterRoleBinding), con mínimo privilegio.
  • NetworkPolicy: por defecto, todos los Pods pueden hablar con todos. Las políticas restringen el tráfico (empezar denegando todo y abrir lo necesario). Las aplica el complemento de red.
  • Protección de la API y de etcd: acceso restringido, TLS y cifrado de los Secret en reposo.
  • Auditoría de las llamadas a la API.
  • Seguridad en ejecución: detección de comportamientos anómalos en los contenedores (Falco).
  • Actualización del clúster dentro de las versiones con soporte.
  • Guías de configuración segura: CIS Benchmarks de Docker y Kubernetes, y las del CCN-CERT para el cumplimiento del ENS (B2-T13).

12. Aplicación al supuesto práctico

Caso típico: un organismo quiere modernizar una aplicación de tramitación, hoy un monolito Java desplegado en servidores de aplicaciones, para desplegar más a menudo y soportar los picos de las convocatorias. Conviene:

  1. Decidir la arquitectura con criterios, no por moda.
    • Primero, contenedores para la aplicación tal cual: es un rehosting que ya aporta despliegues reproducibles.
    • Después, monolito modular o microservicios según el tamaño del dominio, el número de equipos y las necesidades de escalado. Si se opta por microservicios, extraerlos poco a poco con el patrón del estrangulador, empezando por las partes con más carga o más cambios.
    • Una base de datos por servicio solo donde se separen servicios; sagas para los procesos que los crucen.
  2. Plataforma:
    • Kubernetes en el centro de datos propio (OpenShift o Rancher) o gestionado en una nube con cumplimiento del ENS, según la clasificación de la información.
    • Plano de control en alta disponibilidad, nodos en al menos dos zonas, y copias de etcd.
    • Registro privado (Harbor) con análisis de vulnerabilidades y réplica de las imágenes públicas que se usen.
  3. Despliegue:
    • Pipeline de CI/CD con pruebas, análisis de código e imagen, SBOM y firma.
    • Entornos de desarrollo, pruebas, preproducción y producción con la misma imagen y configuración por entorno.
    • GitOps con Argo CD o Flux y manifiestos en Helm o Kustomize.
    • Actualización progresiva por defecto y despliegue canario para los cambios de riesgo; cambios de esquema compatibles hacia atrás.
  4. Escalado:
    • Peticiones y límites medidos, no inventados.
    • HPA con mínimos y máximos, escalado del clúster y, para el procesamiento de colas, KEDA.
    • Prueba de carga previa a la convocatoria y revisión de la capacidad de la base de datos, que no escala igual.
  5. Monitorización:
    • Prometheus y Grafana para métricas, una pila EFK o Loki para registros y OpenTelemetry con Jaeger para trazas.
    • SLO de disponibilidad y tiempo de respuesta del trámite, con alertas sobre ellos.
  6. Seguridad:
    • RBAC de mínimo privilegio, namespaces por aplicación y entorno, NetworkPolicy de denegación por defecto.
    • Nivel Restricted de seguridad de Pods, sin hostPID ni contenedores privilegiados.
    • Secretos en un gestor externo, cifrado de etcd y auditoría de la API.
    • Guías CCN-STIC y medidas del ENS.
  7. Organización: equipo de plataforma que ofrezca estas capacidades como servicio a los equipos de desarrollo, y formación en la nueva forma de trabajar.

La pregunta 2022 · 54 (clasificada en B3-T08) recuerda los tipos de migración: re-alojamiento (rehosting), renovación de la interfaz (refronting), re-arquitectura, sustitución, encapsulado y migración a la nube. Reprompting no existe.

Resumen de repaso

Núcleo de estudio

  • Máquina virtual: el hipervisor virtualiza el hardware; cada máquina tiene su sistema operativo. Tipo 1 sobre el hardware; tipo 2 sobre un sistema operativo. Contenedor: el núcleo virtualiza el sistema operativo; los contenedores comparten el núcleo del anfitrión. Son más ligeros y rápidos, con un aislamiento menor. Se suelen combinar.
  • Aislamiento en Linux: espacios de nombres (PID, mount, network, IPC, UTS, user, cgroup, time) para lo que se ve; cgroups para lo que se consume; capabilities, seccomp y AppArmor o SELinux para lo que se puede hacer.
  • Imagen: plantilla inmutable por capas, identificada por etiqueta o resumen. Contenedor: instancia en ejecución con una capa escribible efímera. Registro: almacena y distribuye imágenes; público para distribuir código abierto, privado para lo propio.
  • OCI: tres especificaciones (imagen, ejecución, distribución). runc ejecuta; containerd y CRI-O gestionan; Kubernetes les habla por CRI.
  • Docker: cliente, demonio y registro. Dockerfile con construcción en varias etapas. Almacenamiento: volúmenes (preferidos), montajes enlazados y tmpfs. Compose para varios contenedores en un servidor.
  • Microservicios: servicios pequeños, por capacidad de negocio, con datos propios y despliegue independiente. Ventajas: despliegue y escalado independientes, aislamiento y autonomía. Costes: sistema distribuido, consistencia eventual, operación compleja. Monolito modular como alternativa razonable. Patrones: pasarela de API, BFF, descubrimiento, saga, bandeja de salida, CQRS, sidecar, malla de servicios, estrangulador. Aplicación de doce factores.
  • Kubernetes: orquestador declarativo con bucle de reconciliación.
    • Plano de control: kube-apiserver, etcd, kube-scheduler, kube-controller-manager y cloud-controller-manager.
    • Nodo: kubelet, entorno de ejecución y kube-proxy.
    • Interfaces CRI, CNI y CSI.
  • Objetos: Pod (unidad mínima, uno o varios contenedores con red compartida); Deployment → ReplicaSet → Pods para cargas sin estado; StatefulSet, DaemonSet, Job y CronJob; Service (ClusterIP, NodePort, LoadBalancer, ExternalName); Ingress y Gateway API; ConfigMap y Secret; PV, PVC y StorageClass; Namespace, etiquetas, cuotas y ServiceAccount.
  • Recursos: peticiones para planificar, límites para acotar. Clases Guaranteed, Burstable y BestEffort. Sondas de arranque, disponibilidad y vida.
  • Soluciones: Helm, Kustomize y operadores; EKS, AKS y GKE; OpenShift y Rancher; contenedores como servicio; serverless.
  • Despliegue: DevOps y SRE. CI (integrar y probar), entrega continua (listo para producción con aprobación) y despliegue continuo (automático). Pipeline con pruebas, análisis, imagen firmada y registro. Infraestructura como código (Terraform, Ansible). Estrategias: recreación, progresiva, azul-verde, canario, A/B y sombra. GitOps: declarativo, versionado, extraído y reconciliado.
  • Monitorización: métricas (Prometheus, Grafana), registros (ELK, EFK, Loki) y trazas (Jaeger), con OpenTelemetry. Señales doradas, RED y USE. SLI, SLO, SLA y presupuesto de error.
  • Escalado: HPA (réplicas), VPA y redimensionado en caliente (recursos), escalado del clúster (nodos) y KEDA (eventos).
  • Seguridad: las 4C; cadena de suministro con análisis, SBOM, firma y SLSA; contexto de seguridad; estándares Privileged, Baseline y Restricted; RBAC, NetworkPolicy, cifrado de Secret y auditoría.

Claves de test

  • Mecanismo preferido de Docker para persistir datos: volúmenes. No bases de datos ni colas.
  • Registro público: para pequeños proyectos de código abierto. Privado: cuando la seguridad es prioritaria o se quiere en las propias instalaciones.
  • hostPID: true = el Pod ve los procesos del nodo. privileged da capabilities y dispositivos, allowPrivilegeEscalation permite ganar privilegios y hostPath da acceso a ficheros, pero ninguno comparte el espacio de nombres de procesos.
  • Contenedor ≠ máquina virtual: comparte el núcleo. Un contenedor Linux no se ejecuta sobre un núcleo Windows sin una máquina virtual.
  • Imagen ≠ contenedor. La etiqueta latest no garantiza la última versión.
  • Las tres especificaciones OCI: imagen, ejecución y distribución. runc es el entorno de referencia.
  • Kubernetes ya no usa Docker Engine directamente (desde la 1.24), pero sí ejecuta imágenes construidas con Docker.
  • Pod ≠ contenedor: es la unidad mínima y puede tener varios.
  • Deployment gestiona ReplicaSets; el ReplicaSet mantiene el número de réplicas.
  • StatefulSet = identidad y almacenamiento estables. DaemonSet = uno por nodo.
  • Service de Kubernetes ≠ microservicio. ClusterIP es el tipo por defecto.
  • etcd guarda todo el estado del clúster. El kube-scheduler asigna Pods a nodos. El kubelet ejecuta los Pods en cada nodo.
  • Secret = Base64, no cifrado por defecto.
  • Readiness saca del balanceo; liveness reinicia; startup protege el arranque lento.
  • Petición = para planificar; límite = máximo. Superar el límite de memoria = OOMKilled; el de CPU = frenado.
  • HPA: réplicas = ⌈ actuales × métrica actual ÷ objetivo ⌉. Necesita peticiones y metrics-server.
  • CI/CD = Continuous Integration / Continuous Delivery (o Deployment). Integración continua ≠ desplegar automáticamente en producción.
  • Entrega continua = listo para producción con aprobación manual. Despliegue continuo = automático hasta producción.
  • Jenkins = servidor de automatización de código abierto en Java. Maven = POM en XML. Ansible = playbooks en YAML. ELK = Elasticsearch, Logstash y Kibana.
  • Azul-verde = dos entornos completos y conmutación instantánea. Canario = porcentaje creciente de tráfico.
  • GitOps = el agente del clúster extrae el estado deseado de Git y lo reconcilia continuamente.
  • Señales doradas: latencia, tráfico, errores y saturación.
  • Microservicios ≠ muchas API pequeñas: lo esencial es el despliegue independiente con datos propios. Base de datos compartida = monolito distribuido.
  • Ingress NGINX se retiró en marzo de 2026; la sucesora de Ingress es Gateway API.
